# Stage-1 Audit Artifact — Contract Surface

> **Area:** API contract surface: OpenAPI v1, spec2.yaml, internal/api/v2, codegen pipeline
> **Generated:** 2026-06-10
> **Scope:** Read-only truth map. No redesign proposals.

---

## 1. Identity & purpose

The contract surface is the machine-readable boundary that describes every public HTTP operation MetalDocs exposes. It consists of one canonical v1 spec (`api/openapi/v1/openapi.yaml`, 5 333 lines), three legacy partial files still under `api/openapi/v1/partials/`, one parallel approval-only spec (`api/openapi/spec2.yaml`, 1 061 lines), and a hand-maintained contract package (`internal/api/v2/`) that pre-dates the v1 oapi-codegen pipeline. The canonical pipeline generates per-module Go server stubs with `oapi-codegen v2.7.0` driven by per-module `cfg.yaml` config files; each stub is committed as `api.gen.go`. The frontend TypeScript types are generated from the same v1 spec with `openapi-typescript`. A bespoke Go lint binary (`scripts/api-lint/`) guards the spec against six contract-drift families: PATH-BASE-PREFIX, ENVELOPE-DRIFT, PAGINATION-DRIFT, AUTHZ-DRIFT, CASING-DRIFT, and five code-side rule families (tripwire-pairing, no-inline-capability, seed/wiki-registry parity, authz-area-scope-binding, no-rawstring-capability, no-rolestring-in-delivery, pagination-codec). All lint rules are CI-blocking with zero allowed violations.

## 3. Public surface

### oapi-codegen generated interfaces (consumed by delivery layer)

Each `api.gen.go` exports a `ServerInterface` that the module's delivery handler must implement. The generated `HandlerWithOptions` / `ServerInterfaceWrapper` mounts the handler onto a `*http.ServeMux`. All modules use `strict-server: true`, which wraps the interface with typed request/response envelope structs.

Generated types from each `api.gen.go` are imported by delivery handlers and, in test files, by contract tests. The `embedded-spec: true` option embeds a gzip-compressed copy of the spec slice into the binary for request validation.

## 4. Logic flows

### Flow 1: oapi-codegen regeneration (backend)

1. Developer or CI calls `go generate ./...` from repo root. (`wiki/references/oapi-codegen.md:8-15`)
2. For each module, Go executes the `//go:generate` directive in `internal/modules/<x>/api/gen.go`, e.g.: `go run github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen --config=cfg.yaml ../../../../api/openapi/v1/openapi.yaml` (`internal/modules/controlleddocuments/api/gen.go:3`)
3. oapi-codegen reads `cfg.yaml` for the target package name, generation flags (`models: true`, `std-http-server: true`, `strict-server: true`, `embedded-spec: true`), and `include-tags` filter. (`internal/modules/controlleddocuments/api/cfg.yaml:1-9`)
4. oapi-codegen reads `api/openapi/v1/openapi.yaml`, filters operations by the declared tags, and emits `api.gen.go` with: typed request/response structs, enum `Valid()` methods, a `ServerInterface` declaring one method per operation, a `ServerInterfaceWrapper` that decodes path/query parameters and calls the interface, and `HandlerWithOptions`/`Handler` registration helpers.
5. The generated file includes a gzip-compressed embedded copy of the spec slice (used for request validation at runtime). (`internal/modules/documents/approval/api/api.gen.go:1`)
6. CI job `backend-codegen-drift` runs `go generate ./...` and asserts `git diff --exit-code -- '**/api.gen.go'`. Any committed stale stub fails the build. (`.github/workflows/api-contract.yml:33-34`)

### Flow 2: frontend TypeScript type generation

1. Developer or CI `cd frontend/apps/web && npm run gen:api`. (`frontend/apps/web/package.json` script `gen:api`)
2. `openapi-typescript` reads `api/openapi/v1/openapi.yaml` (3-level relative path from `frontend/apps/web/`). The output path is `src/lib/api-types/index.d.ts`.
3. The tool emits a `paths` interface keying on each OpenAPI path string, an `operations` interface keying on `operationId`, and component `schemas` / `parameters` namespaces. FE code accesses types through `openapi-fetch` using the `paths` interface as the generic parameter.
4. CI job `frontend-codegen-drift` runs the same command and asserts `git diff --exit-code -- src/lib/api-types/`. (`.github/workflows/api-contract.yml:47-48`)

### Flow 3: api-lint spec rules (PATH-BASE-PREFIX, ENVELOPE-DRIFT, PAGINATION-DRIFT, AUTHZ-DRIFT, CASING-DRIFT)

1. CI job `api-design-system-lint` calls `go run ./scripts/api-lint/ -strict api/openapi/v1/openapi.yaml .`. (`.github/workflows/api-contract.yml:95`)
2. `main.go` calls `RunSpecRules(specPath)`. (`scripts/api-lint/main.go:49`)
3. `RunSpecRules` reads the spec with `gopkg.in/yaml.v3`, navigates the YAML AST, and for each path/operation calls: `checkBasePrefix` (rejects any path key starting with `/api/`), `checkEnvelope` (walks `responses >= 400`, resolves `$ref` in `#/components/responses`, asserts `application/problem+json` content with `$ref: '#/components/schemas/Problem'`), `checkPagination` (list ops must have `cursor`+`limit` query params and `page.next_cursor`+`page.has_more` in 200 response, unless `x-pagination-exempt: true` with a non-empty `x-pagination-exempt-reason`), `checkAuthz` (every op must declare `security` or inherit global security; every state-transition POST must carry `x-authz-area`, `x-authz-area-none`, or `x-authz-custom`). (`scripts/api-lint/spec_rules.go:24-68`)
4. `checkCasing` does a full tree walk for every `properties:` map and `parameters:` sequence, asserting `snakeCaseRE = ^[a-z][a-z0-9]*(_[a-z0-9]+)*$` on each property key and query/path param name, with a hardcoded exemption for `MDDM_NATIVE_EXPORT_ROLLOUT_PCT`. (`scripts/api-lint/spec_rules.go:96-157`)
5. Any violation produces a `Violation{File, Line, Rule, Message}`. With zero violations `main` exits 0; with any violations it prints all violations and exits 1. (`scripts/api-lint/main.go:74-81`)

### Flow 4: api-lint code rules (tripwire-pairing, registry binding)

1. `RunCodeRules(specPath, modulesRoot, strict)` is called from `main` when a repo root arg is provided. (`scripts/api-lint/main.go:55-62`)
2. `checkTripwirePairing` walks `internal/modules/**/*repository*.go` files, parses each with `go/parser`, and for each function scans: presence of `authz.Require` / `authz.RequireAll` call (any); presence of `Exec` / `ExecContext` call with a SQL literal containing `INSERT INTO`, `UPDATE`, or `DELETE FROM`. A function with mutating SQL but no authz call is flagged unless its `<rel-path>|<FuncName>` key appears in `scripts/api-lint/tripwire-allowlist.txt`. Stale allow-list entries (matched by no live violation) are also flagged. (`scripts/api-lint/code_rules.go:133-225`)
3. `RunRegistryRules` calls six additional checkers that parse `internal/modules/iam/domain/model.go` to extract the canonical `Capability` and `Role` const-value maps, then walk the codebase asserting: no `Capability("literal")` conversion outside the registry file (`checkNoInlineCapability`), every seeded capability in `db/reference-data/0001_product_reference_data.sql` exists in the registry and vice versa (`checkSeedRegistryParity`), every `` `cap:<name>` `` marker in `wiki/concepts/authz-tiers.md`, `wiki/references/local-dev-credentials.md`, `wiki/modules/iam.md` exists in the registry (`checkWikiCapabilityParity`), no area-grade capability called with literal `"tenant"` as the area arg (`checkAuthzAreaScopeBinding`), no raw string literal capability to `authz.Require` (`checkNoRawStringCapability`), no role-name string literal in a delivery/http authz gate (`checkNoRoleStringInDelivery`). (`scripts/api-lint/registry_rules.go:61-104`)
4. `checkPaginationCodec` walks all non-generated non-test `.go` files and flags any reference to `base64.StdEncoding` outside the canonical `internal/platform/pagination/cursor.go`. (`scripts/api-lint/code_rules.go:79-131`)

### Flow 5: request validation at runtime (embedded spec)

When a module registers its handler using `HandlerWithOptions` the generated `ServerInterfaceWrapper` uses the embedded spec bytes (decompressed from `flate`-compressed base64) and `github.com/getkin/kin-openapi/openapi3` to validate incoming requests against the spec fragment. This is enforced at the delivery layer boundary before the handler method is called. (`internal/modules/documents/approval/api/api.gen.go:1-26`; `embedded-spec: true` in all `cfg.yaml` files) [runtime-unverified: whether `RequestValidatorOptions` is actually wired in the composition root — oapi-codegen emits the capability but the caller can opt out]

## 6. Persistence

None. The contract surface files are pure schema/code-generation artifacts. They do not own database tables or issue queries. The `api-lint` code-side rules read files from disk (Go source, SQL seeds, wiki Markdown) but perform no DB interaction.

## 7. Config & environment

- **oapi-codegen**: no env vars consumed; driven by per-module `cfg.yaml` and the spec file path passed on the CLI via `//go:generate`.
- **api-lint**: invoked with two positional arguments (`<spec-path>` and `[<repo-root>]`) and flags (`-strict`, `-only`). No env vars. `-strict` converts missing core files into hard errors; used in CI. (`scripts/api-lint/main.go:18-42`)
- **Frontend type generation** (`gen:api`): no env vars; uses fixed relative path `../../../api/openapi/v1/openapi.yaml` baked into `package.json`.
- **CI** (`api-contract.yml`): no secrets; uses `actions/setup-go@v5` with `go-version: 1.25.x` and `actions/setup-node@v4` with `node-version: 20.11.0`.

## 8. Concurrency & async

None. All components in this area are build-time or CI-time tools (code generation, linting). No goroutines, channels, or async patterns exist in the contract surface itself.

## 9. Error handling & observability

**api-lint (`scripts/api-lint/`)**: errors are written to `os.Stderr`; violation lines are written to `os.Stdout` as `<file>:<line>: <RULE>: <message>`; exit code 1 on any violation, 2 on argument error. (`scripts/api-lint/main.go:74-81`) No structured logging, no metrics.

**Generated `api.gen.go` files**: the generated `ServerInterfaceWrapper` returns HTTP 400 with a plain text body on parameter binding failure. Actual RFC 9457 `problem+json` error formatting for business errors is the responsibility of the handler implementation — it is not generated. (`internal/modules/documents/approval/api/api.gen.go` — wrappers call `http.Error` on decode failure) [runtime-unverified: whether all parameter error paths actually produce `problem+json` or bare `http.Error`]

**spec2.yaml error schema**: uses a non-Problem error shape `ErrorResponse { error: { code, message, details }, request_id }` rather than RFC 9457 `Problem`. (`api/openapi/spec2.yaml:596-606`) This diverges from the v1 contract's `Problem` schema.

## 10. Legacy / duplication / smell flags

- **CASING-DRIFT in partials: `api/openapi/v1/partials/controlled-documents.yaml`** — All schema property names are camelCase (`tenantId`, `profileCode`, `processAreaCode`, `ownerUserId`, `createdAt`, `updatedAt`, `areaCodes`, `userIds`, `profileCode`, `areaCode`, `nextSeq`, `documentId`, `approvalState`, `contentHash`, `revisionVersion`, `publishedDocumentId`, `approvalInstanceId`) and the request/response properties are also camelCase. The v1 canonical spec defines the same resource (`ControlledDocument`) with snake_case at `api/openapi/v1/openapi.yaml:5000-5031`. The api-lint CASING-DRIFT rule does NOT run against partials — only against the canonical spec. The partial is **not referenced by any codegen config** and is therefore dead from a pipeline perspective, but its continued existence creates confusion. (`api/openapi/v1/partials/controlled-documents.yaml:207-305`)

- **CASING-DRIFT in partials: `api/openapi/v1/partials/documents.yaml`** — Response for `createDocument` returns PascalCase fields `DocumentID`, `InitialRevisionID`, `SessionID` (`api/openapi/v1/partials/documents.yaml:47-51`). Also uses `/api/v1/` path prefix and has no `operationId` on most operations. Not consumed by any codegen config.

- **PATH-BASE-PREFIX in all three partials** — All partial files use `/api/v1/...` path keys (e.g. `api/openapi/v1/partials/controlled-documents.yaml:2`), which the canonical spec prohibits (servers.url already carries `/api/v1`). The api-lint PATH-BASE-PREFIX check does not run against these files.

- **Parallel surface: `api/openapi/spec2.yaml` (RF-4 open item)** — spec2.yaml defines 13 approval state-machine routes (`/documents/{id}/submit`, `/approval/instances/...`, etc.) that overlap in HTTP path with approval operations already declared in `api/openapi/v1/openapi.yaml` under the `approval` tag. spec2.yaml uses its own `ErrorResponse` schema (non-Problem). It is not used by any `//go:generate` invocation and is not linted by api-lint. Its last commit was `e1944bc4a "refactor(api): purge v2 routes and apply plan10 schema cleanup"`. The corresponding `internal/api/v2/` package is imported only by contract tests. This constitutes a parallel, unfenced, unlinted spec surface — RF-4 in the target architecture register. (`api/openapi/spec2.yaml:1-30`, `wiki/architecture/backend-target-architecture.md:200`)

- **`internal/api/v2/types_gen.go` filename "gen" misnomer** — The file is named `types_gen.go` but is not generated by any tool (`//go:generate` is absent). It is a hand-maintained file. The `_gen.go` suffix implies machine-generated origin and is reserved by convention for oapi-codegen output. Any tool skipping `*.gen.go` files (including the api-lint pagination-codec check at `scripts/api-lint/code_rules.go:97`) will silently exempt this hand-maintained file. (`internal/api/v2/types_gen.go:1`)

- **`apiv2.APIError` vs `v1 Problem` — parallel error type for tests** — The `apiv2.APIError` type (`internal/api/v2/types_gen.go:55-60`) uses a flat `{Code, Message, Details, TraceID}` shape while the canonical v1 error is `Problem {title, status, code, detail, instance, errors}`. Contract tests decode responses into `apiv2.APIError` which is a structurally different type than the spec-declared `Problem`. The tests pass because `json.Unmarshal` is tolerant of missing fields, but the type does not faithfully represent the `application/problem+json` contract. (`internal/api/v2/types_gen.go:55-60`, `internal/modules/iam/delivery/http/routes_memberships_contract_test.go:109-114`)

- **`iamapi` cfg.yaml bundles three tags** — `internal/modules/iam/api/cfg.yaml` includes tags `[iam, audit, security]` generating a single `api.gen.go` that is 5 691 lines. The IAM, audit, and security concerns are distinct domains that happen to share a generated package. This creates a very large generated file and couples the three concerns' regeneration. (`internal/modules/iam/api/cfg.yaml:9-11`)

- **`documents/api/api.gen.go` is the largest generated file at 6 213 lines** — The `documents` tag produces the largest stub file. Documents is also the largest module (184 files per backend-blueprint.md). No issue per se but a signal that the documents API surface is proportionally large. (`internal/modules/documents/api/api.gen.go`)

- **Legacy `POST /iam/users` route marked "legacy; prefer POST /iam/users/invite"** — The description of `createManagedUser` at `api/openapi/v1/openapi.yaml:213` explicitly calls this route legacy but it remains in the spec with no deprecation marker (`deprecated: true`) in the OpenAPI sense. A consumer reading the spec without the description note has no machine-readable signal of its status.

- **`api/openapi/spec2.yaml` has no `security` global or per-operation** — Unlike the v1 spec which has a global `security: - sessionCookie: []` default, spec2.yaml has no global or per-operation security declarations. The AUTHZ-DRIFT rule does not run against spec2.yaml, so this goes unchecked. (`api/openapi/spec2.yaml:1-30`)

- **Partial files reference `#/components/schemas/` schemas not present in the partials themselves** — `api/openapi/v1/partials/controlled-documents.yaml` uses `$ref: '#/components/schemas/ControlledDocumentVisibility'` etc. at line 221 and defines its own `ControlledDocumentVisibility` with camelCase `areaCodes`/`userIds`. The canonical spec defines the same schema with snake_case `area_codes`/`user_ids` at `api/openapi/v1/openapi.yaml:5020-5030`. These are two divergent definitions of the same resource with different wire keys.
