# ADR 0070 — Tenant lifecycle: onboarding API, per-module export/erasure ports, and crypto-shred erasure with an immutable audit skeleton

> **Status:** Accepted 2026-07-05
> **Modules:** `iam` (tenant onboarding + lifecycle orchestrator, capability registry) · `security` (per-tenant key envelope) · `audit` (immutable skeleton + crypto-shred payload) · `documents` · `templates` · `controlleddocuments` · `documents/approval` · `notifications` · `render` · `taxonomy` (each publishes a `TenantDataPort`) · `internal/platform/db` + migrations + `tests/integration/testdb` (F7.4 RLS-truth sweep)
> **REQ IDs:** `backend-target-architecture.md` REQ-AUTHZ-5 (capability coherence), REQ-TENANT-* (pooled multi-tenancy / RLS), REQ-DB-* (DB-enforced invariants), REQ-AUDIT-* (append-only hash chain)
> **Supersedes / amends:** none. Extends ADR 0022 (capabilities-never-roles) with three new capabilities; extends the M2 tripwire-generation mechanism (migrations 0269/0270/0271/0275) with the M7 arm migration; complements ADR 0027 (tenancy NULL-permissive + async posture) and ADR 0067 (async on River). Reaffirms the audit append-only immutability grant (`0266`).
> **Gate:** `docs/superpowers/analysis/2026-07-05-m7-tenant-lifecycle-system-impact.md` (developing-new-work, Yellow — no AS-1/AS-2/AS-3).

## Context

Finding 15 of the 2026-07-03 final architecture review, and the canon "Data lifecycle" rule (`wiki/standards/backend-canon.md:181` — T-003: retention, GDPR-class erasure, backups with tested restore), name a kernel gap: MetalDocs has **no tenant lifecycle**. Runtime-truth census (2026-07-05, gate §runtime facts) confirmed:

- **No onboarding.** `metaldocs.tenants` (`id`, `name`, `slug`) exists only via bootstrap SQL / dev-seed. There is no programmatic path to create a tenant, seed its first admin, and grant capabilities.
- **No export, no erasure.** Neither a tenant-scoped data export nor an erasure path exists.
- **Audit immutability vs GDPR erasure collide.** `metaldocs.audit_events` has `UPDATE`/`DELETE`/`TRUNCATE` **revoked** (`0266_audit_events_hardening.sql:119`) and a real hash chain (`row_hash` over `prev_hash` + row fields, serialized by `pg_advisory_xact_lock`, `writer.go:59`). GDPR's right-to-erasure requires a tenant's PII to become unrecoverable — which naive row deletion cannot deliver without violating invariant 5 (DB-enforced immutability) and breaking the chain.
- **Tenant data is cross-cutting.** 34 `tenant_id` tables span ~9 modules; blob keys are already tenant-namespaced (`tenants/{tenant_id}/…`, `documents/application/keys.go:12`).
- **F7.4 — RLS false-green.** Dev/CI `metaldocs_app` is **SUPERUSER + BYPASSRLS**, so FORCE RLS (33 tables + uniform `tenant_isolation` policy) is **inert in dev** → tenant-isolation integration tests are false-green. Prod is NOSUPERUSER+NOBYPASSRLS (safe) — this is a *test false-negative*, not a prod leak. **Owner-bypass trap:** FORCE RLS never applies to a table's owner, so flipping the role attributes alone is insufficient unless the CI role is also a **non-owner**. Newly surfaced: `public.approval_signoffs` carries `actor_tenant_id` with **no FORCE RLS / no policy** — isolation rests solely on the `enforce_signoff_tenant_consistent()` trigger.

The capability-registry bump convention (`iam/domain/model_test.go:96` — "bump only via ADR") makes this ADR a gated deliverable of F7.1. Operator forks resolved 2026-07-05: erasure = crypto-shred; onboarding = API; F7.3 = implemented; orchestrator home = iam service.

## Decision

1. **Onboarding is a contract-first API into an `iam` application service.** A new `POST /tenants` route (`api/openapi/v1/openapi.yaml` → regen) invokes an `iam` `OnboardTenant` service that, in one `TxRunner` tx, inserts the `metaldocs.tenants` row, seeds the first admin `iam_users` principal + role/capability grants, provisions the tenant's crypto key (decision 4), and audit-records the onboarding event. Manual seed-only tenant creation is retired for the runtime path. **Acceptance:** a newly onboarded tenant is reachable end-to-end — login as its admin → a capability-gated action — proven by a live QA drive.

2. **Export and erasure fan out over a per-module `TenantDataPort`, never a god-query.** Each module owning `tenant_id` tables publishes a `TenantDataPort` (`ExportTenantData(tenantID) → artifact-part`, `EraseTenantData(tenantID)`), owning its own semantics. A thin **lifecycle orchestrator hosted in `iam`** calls every registered port. This is load-bearing for invariant 6 (cross-module access only via published interface) and kills the hand-sync rot class (a new tenant table is invisible unless its owning module updates *its own* port). **A coverage test asserts every module owning a `tenant_id` table registers a `TenantDataPort`** — the census is a test, not human vigilance. Rejected: a central function enumerating all 34 tables (violates invariant 6; rots on every schema addition; centralizes per-module shred/delete rules it cannot own correctly).

3. **Export = a complete tenant-scoped artifact.** The orchestrator assembles each port's export into one artifact: a JSON manifest of all tenant rows plus the tenant's blobs (already under the `tenants/{tenant_id}/…` prefix), written back to the tenant blob namespace. Long-running/external → built as an idempotent async job on River (ADR 0067) via the transactional outbox, never inline in the handler tx. Capability-gated (`tenant.export`).

4. **Erasure = crypto-shred the per-tenant key; the audit skeleton is never mutated.** PII is encrypted behind a **per-tenant data key** owned by `security` (a key-envelope framework — DEK-per-tenant wrapped by a KEK; if no such primitive exists it is built as a platform/security framework, not inlined). Erasure **destroys the tenant's key**, rendering all PII ciphertext mathematically unrecoverable, and writes an **erasure tombstone** audit event recording *that* the erasure occurred. Audit rows are **never** `UPDATE`d or `DELETE`d — the append-only grant (`0266`) and the hash chain stay byte-intact, so chain-validation stays **GREEN post-erasure** (proven by an integration test that erases, then re-runs chain validation). The PII-bearing surface is `audit_events.payload` (jsonb) plus any PII fields elsewhere placed behind the per-tenant envelope; the non-PII **skeleton** (`id`, `actor_id`, `action`, `resource_type`/`_id`, `tenant_id`, timestamps, `prev_hash`, `row_hash`) survives to prove an event happened without exposing the person. Capability-gated (`tenant.erase`, `system_admin`-class). **Rejected:** hard-delete of tenant rows including audit — violates invariant 5 and the append-only grant, breaks the chain, defeats the regulated tamper-evident trail. This is the standard GDPR-vs-immutability resolution.

5. **Three new capabilities, tripwire arms generated (M2), registry 35→38.** `tenant.onboard`, `tenant.export`, `tenant.erase` are declared in the `iam` registry, scope-classified, tier-1 route-mapped (`permissions.go`), tier-2 `authz.Require`-gated in-tx, seeded to the appropriate holders (`tenant.erase` to `system_admin` only), and their DB tripwire arms **generated from the registry** per M2 (no hand-sync). `TestCapabilityRegistrySize` bumps 35→38 (the one mandatory manual edit, gated by this ADR). H-PRE-1 holds: any audit-recording `authz.Require` in the erasure fan-out stays **off** the audit-writer's advisory-lock tx.

6. **F7.4 — CI/dev DB role becomes NOSUPERUSER + NOBYPASSRLS + non-owner; the existing integration suite is the census.** Table ownership is reassigned away from the app role (closing the owner-bypass trap), and the app role loses SUPERUSER/BYPASSRLS in dev/CI — matching the prod deployment constraint (ADR 0022 Phase-5 §7 / ADR 0027). Every tenant-scoped query that relied *solely* on RLS flips its isolation test **RED** under the prod-faithful role; each is fixed with an explicit `tenant_id` predicate (correct-by-construction, as M6 F6.4 did for the two review-due ports). A **lint blocks new sole-RLS tenant-scoped reads/writes**. **`approval_signoffs`** gains a real FORCE RLS + `tenant_isolation` policy on `actor_tenant_id` for parity with the other 33 tables; if the signoff cross-tenant semantics (co-sign across tenants) genuinely require the trigger instead of a policy, that exception is recorded here in a follow-up amendment with the lint carve-out — **no silent special-case**. **Negative + positive proof mandatory:** a sole-RLS query leaks under the wrong tenant / is blocked under the right one, for real, under the non-bypassing role.

7. **F7.3 is implemented this milestone, not design-only.** Export produces a real artifact; erasure really shreds the key and the post-erasure chain-validation test runs GREEN — both under the canonical `testdb` integration framework. (Mission's "implemented preferred" bar, operator-elected.)

## Consequences

- **Positive.** Tenant lifecycle becomes a designed kernel: onboarding is self-serve + auditable; export is complete + tenant-scoped; erasure is GDPR-compliant *and* keeps the regulated audit trail immutable and chain-valid. The per-module port + coverage test makes lifecycle coverage drift-proof. F7.4 makes tenant isolation genuinely tested (prod-parity), converting 33 previously-false-green tables into real proofs and closing the `approval_signoffs` gap.
- **Costs / risks.** A per-tenant key-management primitive is net-new cross-cutting surface (`security`) — the highest-risk piece; key loss = unintended erasure, so key provisioning is part of onboarding (decision 1) and key destruction is the single audited erasure act. Reassigning table ownership (F7.4) is an expand/contract migration that must not break the live schema in one step. Each module gains a `TenantDataPort` to maintain — the coverage test is the guard.
- **Follow-ups (bounded).** Offboarding / suspension / plan-change lifecycle events are out of scope (trigger: when billing or self-serve suspension lands); if they arrive, the `iam`-hosted orchestrator is promoted to a dedicated `tenantlifecycle` module then. Backups-with-tested-restore (canon T-003) is M8 ops posture, not M7.

## Validation

Per D4, the M7 `validation-contract.md` (authored before implementation) enumerates: the exact `tenant_id` table inventory in/out of erasure scope; the per-module `TenantDataPort` set + coverage test; the onboarding end-state (login → capability-gated action); the export artifact shape (manifest + blob manifest); the crypto-shred mechanism + the audit-chain-stays-GREEN post-erasure proof; and the exact sole-RLS query set surfaced by the F7.4 role flip. Milestone-validator judges implementation against that contract.
