## 1. Classify & own

- **Work type:** feature (extends an existing surface — the approval worklist — to a second subject kind; no new module, no new capability).
- **Owning module(s):** `approval` (top-level module 15) — owns `approval_instances`, the worklist read-model (`ListWorklist`, `read_service.go:545`), and the `/approval/inbox` route. `frontend/apps/web/src/features/approval` owns the inbox UI.
- **Explicitly NOT owning:** `templates` — does not own the worklist; it only *provides* template-version display data through an approval-owned port. `documents` — the document worklist path is unchanged (not re-owned, not refactored).
- **Cross-module edges (with direction):**
  - `approval → templates` (existing edge, extended): approval reads template display meta (templateId + name) via the approval-owned `TemplateVersionReader` port (`application/template_submit_service.go:28`), adapter in `templates/infrastructure/approval_version_reader.go`. **New method added to the existing port** — never a raw join into `templates_template*`. Boundary preserved.
  - `approval → documents` (existing edge, UNCHANGED): the worklist keeps its existing `LEFT JOIN documents` for document rows. Not extended, not deepened.
  - `frontend/features/approval → templates route` (FE nav): template inbox rows link to `/templates/:templateId/approval` (existing route). Legitimate — the FE talks to both surfaces.
- **Ambiguity?** None. `approval` unambiguously owns the worklist. No AS-3.

## 2. Foundation verdict

- **Base you'd build on:** `ListWorklist` is a read-model projection that today `SELECT`s `ai.document_id` + `LEFT JOIN documents d` to embed `doc_title`/`controlled_document_id`. `approval_instances` is already subject-generic since migration 0296/0297 (`subject_kind`, `subject_key` NOT NULL; `document_id` relaxed to NULL for template rows). Template kernel instances already exist (subject_kind='template', subject_key=version_id) — they are simply invisible to the worklist (no subject discriminator selected, document join misses → blank rows).
- **Sound, or legacy/patch/workaround?** The kernel foundation is **sound** (extracted + validator-PASS in 3.1). The worklist's raw `LEFT JOIN documents` is a **mild pre-existing boundary smell** (approval SQL naming another module's table) but functionally sound, reviewed, and grandfathered. The same file already uses the **boundary-clean reader idiom** for area code (`cdRead.ProcessAreaCode`, `read_service.go:929`).
- **GM-fork record (HARNESS §3 — 2 shapes compete):**
  - **A** — extend the raw `LEFT JOIN documents` pattern with `LEFT JOIN templates_template_version → templates_template`. Consistent with the existing join, no migration. **Rejected:** grows the boundary smell (adds a SECOND module's table to approval SQL) — violates the no-deepening rule; a domain reviewer should flag it against invariant 6.
  - **B** — add `subject_title_snapshot` (+ `subject_ref`) columns to `approval_instances`, populated at submit time by each subject path. **This is the global maximum:** single-table worklist read, zero cross-module resolution, matches the pervasive `*_snapshot` idiom, drift-immune. **Crosses this unit's boundary:** requires a migration, and Track C owns `0306+` exclusively this batch (collision matrix forbids Track A a migration). → Filed as **named debt** (§10) with a reopen trigger. This is GM-fork route (b): land a boundary-consistent bridge now, name B for a future named unit.
  - **C (CHOSEN bridge)** — worklist selects `ai.subject_kind`/`ai.subject_key` (approval's OWN columns); document rows keep the existing join UNCHANGED; template rows resolve `{templateId, name}` via the approval-owned `TemplateVersionReader` port (new batch method) AFTER the query. Boundary-clean (grows the *sanctioned port pattern*, not the smell), no migration, respects the no-deepening rule (documents base untouched). Cost: N reader round-trips for template rows per page (bounded by `ClampLimit`). Reversibility: when B lands, the reader call becomes dead code — trivially removed; no data written in the wrong shape. Passes the reversibility veto.
- No AS-2: the chosen bridge does not optimize *inside* a patch — it uses the clean port seam and leaves the document base as-is.

## 7. Contract & data

- **OpenAPI-first:** `ApprovalInboxItem` redefined subject-generic: `instance_id`, `subject_kind` (enum document|template), `subject_key`, `subject_title`, `subject_ref` (FE nav id: documentId | templateId), `controlled_document_id` (nullable — documents only), plus unchanged `area_code`, `submitted_by`, `submitted_at`, `stage_label`, `quorum_progress`, `stage_kind`, `due_at`. **DROP** `document_id` + `document_title` (hard break per [[legacy-fallback-extermination]] — no relax-to-optional; the sole consumer, the approval inbox FE, is updated in the same unit). Regen `approvalapi`.
- **Migration:** **NONE** (Track A adds no migration; Track C owns 0306+). `subject_kind`/`subject_key` columns already exist. If the design later demands a column, emit `REQUEST migration-number` — never grab blind.
- **Destructive change?** The wire-contract field drop is contract-breaking but the ONLY consumer is in-repo (approval inbox FE), updated atomically in this unit's slice 2 — no external contract consumer (finding 18/19 confirm inbox has no external chaining consumer). Single-repo hard break is the ratified MetalDocs pattern, not an expand/contract deferral.
