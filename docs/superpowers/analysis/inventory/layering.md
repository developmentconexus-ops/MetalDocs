## The five heaviest, with detail

**LAYERING-08/09/10 (foreign-table SQL reads, 17+ sites across 3 module pairs).** `approval` and `documents` each read the other's tables directly with hand-written `JOIN`/`FROM` SQL instead of going through the owning module's repository or application service, and `approval` does the same into `controlleddocuments`. This is the sharpest violation of REQ-TOP-1 ("never another module's repository, SQL, or domain internals") because it is invisible to any Go-level boundary check — `scripts/check-module-boundaries.ps1` cannot see inside a SQL string literal. It also means the `TenantDataPort.Tables()` ownership declarations used for tenant export/erasure are aspirational: the module that declares ownership is not the only module that can mutate query behavior against those tables' shape (a column rename in `documents` requires grepping SQL strings across `approval`, not just recompiling).

**LAYERING-03/04 (producer-owned types/functions/interfaces at 6+ sampled cross-module seams).** Neither direction of the `documents`↔`approval`↔`controlleddocuments`↔`taxonomy`↔`iam`↔`security` seams shows a consistent "consumer declares the interface it needs" discipline. Sometimes the consumer imports a producer struct and free function directly (`documents/application` calling `controlleddocumentsdomain.Resolve(...)`); sometimes the consumer's constructor is typed by a producer-declared interface (`security` taking `iamdomain.UserDisplayNameReader`). Both defeat the purpose of a port: the producer can change either the type or the interface shape and every remote consumer recompiles or breaks, because there is no consumer-side seam to insulate against it. LAYERING-05 shows the repo already knows the correct shape (consumer-declared interface + composition-root adapter) and applies it exactly once, for `tokens`.

**LAYERING-01/02 (9 of 15 domain packages import `database/sql`/`platform/db`).** Every port interface that needs to run "inside the caller's transaction" is typed directly with `*sql.Tx` (or the structurally-equivalent `platform/db.Tx`) rather than a domain-owned transaction abstraction. This is well short of "domain has zero infrastructure imports," the implied bar from the target architecture's `domain → application → infra → delivery` layering diagram (REQ-TOP-1's neighbor, `backend-target-architecture.md:33`). It is consistent and repo-wide rather than an isolated slip, which suggests it is a deliberate (if unlabeled) convention, not an accident — the synthesis step should treat it as a policy question, not 9 independent bugs.

**LAYERING-07 (62 cross-module `errors.Is` sentinel checks).** Every one of these is an undeclared contract: nothing marks `authdomain.ErrIdentityNotFound` or `taxonomydomain.ErrAreaArchived` as part of a published cross-module surface, so nothing would catch a rename. They cluster heavily in `delivery/http` error-mapping switches (`iam/delivery/http/*`, `controlleddocuments/delivery/http/routes.go`, `templates/delivery/http/errors.go`), which is defensible as "delivery translates errors to HTTP" — but the translation target is still the producer's raw sentinel, not an adapter-owned error type, so the coupling is real even where the layer is nominally allowed to see it.

**LAYERING-11/12/13 (fan-in concentration + platform module-coupling, already partly known).** `iam/domain` (32 importers) and `iam/authz` (26) sit at the top of the whole graph's fan-in, ahead of all but two platform packages — any change to `iam/domain`'s exported surface has blast radius comparable to changing `platform/db`. Separately, 5 platform packages beyond the already-known `tenantdata` importer set (`bootstrap`, `authn`, `docgenv2`, `tripwire`, `worker`) import specific modules' `domain`/`application` packages; `docgenv2` in particular imports `documents/application` and `documents/domain` by name, which reads as document-rendering logic housed under `platform` rather than generic infrastructure — evidence only, ownership judgment left to synthesis.

## What is actually fine

- **Zero package-level import cycles.** Go's compiler forbids them and none exist (`go build ./...` succeeds; Tarjan SCC over the full 136-package graph found no multi-node strongly-connected component). The 7 known *module*-level cycles are all broken cleanly at the package boundary — by depending on the other module's `domain` (or a same-named leaf package) rather than a package that imports back, not via any setter-injection or interface-in-the-middle trick. No "awkward means" (post-construction setters breaking a would-be cycle, duplicated parallel types) were found anywhere in the sampled seams — the repo simply routes around cycles by always importing `<module>/domain`, never the top-level or `application` package, from the reverse direction.
- **Zero intra-module layer inversions at the Go-import level** (LAYERING-14): no `domain` package anywhere imports its own module's `infrastructure` or `delivery`; no `application` package imports its own module's `delivery`. Whatever discipline is missing, this one is enforced without exception across all 15 modules.
- **The `dictionary_reader_adapter.go` pattern** (LAYERING-05) — consumer-declared interface, composition-root adapter, explicit comment naming the invariant it protects — is a correct instance of exactly the discipline the other seams lack. It proves the team knows the pattern; the inconsistency is the finding, not ignorance of the pattern.
- **`main.go`'s hand-wiring is not itself a defect at this size.** 1312 lines with 51 module imports and 3 setters is unglamorous but legible — there is no hidden DI magic, no reflection-based container, and the wiring is traceable top-to-bottom by reading the file. Whether it *should* stay this way as modules grow is a synthesis question, not a discovery finding.
- **Domain packages are free of literal SQL.** Every apparent "domain has table names" hit on inspection was a doc-comment (`documents.planned_effective_from`, `taxonomydomain.AreaCatalogReader` mentions) — no `domain` file constructs or issues a SQL string; all raw SQL lives in `infrastructure`.

## Unverified / needs judgment

- Is the domain-wide `*sql.Tx`/`platform/db.Tx` parameter convention (LAYERING-01/02) an explicit, ratified convention somewhere (an ADR I did not find), or truly unlabeled? I searched `wiki/decisions/` headings only, not full text of every ADR — could not confirm either way.
- For the 62 cross-module `errors.Is` sites (LAYERING-07): how many are in `delivery` layers, where the target architecture arguably permits error-to-HTTP translation to reach into producer internals, versus in `application` layers, where it should not? I did not classify all 62 by layer — the count is real, the layer breakdown is not.
- Are `security`'s and `iam`'s producer-owned-interface dependencies on each other's `domain` packages (LAYERING-04) intentional "shared vocabulary" akin to the sanctioned capability-constants pattern (`wiki/architecture/backend-target-architecture.md:132`), or accidental? The capability-constant case is explicitly sanctioned in the target architecture; these reader interfaces are not mentioned anywhere I found.
- `internal/platform/docgenv2` importing `documents/application` and `documents/domain` directly (LAYERING-13) — is this genuinely document-rendering-as-a-platform-service (defensible), or documents-module logic that should live under `internal/modules/documents`? I report the fact only; the register asks synthesis to rule on placement, not this lane.
