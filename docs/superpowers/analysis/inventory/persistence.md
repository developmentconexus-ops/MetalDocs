## The five heaviest, with detail

**PERSIST-02/PERSIST-01 (hand-rolled tx vs TxRunner, 82 sites / 25 files).** The platform layer ships a single `TxRunner` port explicitly designed so "a service can no longer leak a transaction or forget to commit" (`runner.go:20-22`), but three-quarters of repository constructors (75 of 81 sampled) never receive it — they take `*sql.DB` and call `BeginTx` themselves, and two modules (taxonomy, iam-membership) went further and defined their own second port with the same shape. Every one of those 82 sites re-implements the exact begin/defer-rollback/commit dance the shared port exists to centralize. This is the load-bearing maintainability cost in this lane: a future TxRunner-level change (e.g. adding a retry, a metric, an isolation-level policy) has to be hand-propagated to 25 files instead of one.

**PERSIST-04 (dead pq.Error fallback + inconsistent unique-violation detection, 15 sites / 10 files).** The process registers only the `pgx/v5/stdlib` driver, yet 5 files still carry a `lib/pq`-typed error-code fallback that structurally can never fire. This is a correctness smell of the class that survives code review because it "looks defensive" — it costs nothing today because the pgx check always wins first, but it is dead code duplicated per file, and any future driver swap or refactor that reorders the checks would silently break unique-violation detection.

**PERSIST-05 (100% hand-written SQL + inline scan boilerplate, 242 scan sites vs 16 helpers).** There is no schema-checked query layer anywhere in the codebase — every query, every column list, every `.Scan()` argument list is maintained by hand and kept in sync with the domain struct and the `SELECT` column order by eye. 242 scan sites against 16 factored helpers means roughly 93% of scans are one-off. This is the single largest hand-sync surface in the persistence layer: a column rename requires grep-and-fix across every query that touches it, with no compiler check that a `Scan()` argument list still matches its `SELECT` list.

**PERSIST-09 (baseline-equivalence check not wired to CI).** The one tool that guarantees "baseline == migrate-from-zero" — the exact invariant `CLAUDE.md` and the migrations README depend on — is a manual PowerShell script requiring a live `docker exec` against a running Postgres container, run at the operator's discretion. Gapless/no-historical-edit IS enforced in CI (`invariants.yml:migration-gapless`), but equivalence of the curated baseline SQL to the historical migration chain it replaced has no automated gate, so a divergence there would only surface as a runtime schema mismatch, not a CI failure.

**PERSIST-03 (DoReadOnly never used, 0 of 67 sites).** The read-only transaction variant exists, is documented with a subtle authz interaction warning (the `authz.Require` F8 bypass-audit INSERT rejects READ ONLY tx), and is called from nowhere. Per the standing memory note this was a deliberate G1 resolution (DoReadOnly → Do + an api-lint guard) rather than an oversight, but the port itself is now dead surface area: every read path runs read-write, forgoing the write-guard DoReadOnly was built to provide.

## What is actually fine

- **Tenant predicate discipline is strong.** Of 87 files issuing raw SQL, only 4 lack any `tenant_id` mention, and 3 of those are legitimately tenant-agnostic (global catalogs, system janitors). This is not the free-for-all a codebase this size could easily have.
- **Parameter binding is clean.** Every dynamic-`WHERE` site sampled (`buildDocumentFilter` and its 3 consumers) binds values as `$N` placeholders, never string-concatenates user input into SQL text. The `%s` interpolation only ever substitutes a pre-built clause of `column = $N` fragments, not raw values. No live injection surface found in this lane.
- **The outbox pattern is centralized and consistently owned.** `INSERT INTO metaldocs.outbox_events` has exactly one call site (`internal/platform/messaging/outbox/postgres/publisher.go:30`); the render/PDF fanout path (`internal/modules/render/fanout/reconstruction.go`) makes its external HTTP call (`client.Fanout`) outside any DB transaction, reading inputs and writing the forensic record as separate, non-transactional steps — no state-write shares a tx with a network call in the sampled path.
- **Migration hygiene is CI-enforced where it matters most.** Gapless sequencing and no-historical-edit are both checked by `.github/workflows/invariants.yml:migration-gapless`, not left to discipline alone.
- **Schema-level invariants are substantial and DB-enforced, not just app-side.** 108 CHECK constraints, 59 FKs, 38 triggers, 31 unique indexes, 37 RLS policies in a 5,054-line baseline. The one cross-checked example (document status transitions) is enforced by both an app-side function (`CanTransitionDocumentStatus`) and a DB trigger (`enforce_document_transition`, `db/baseline/0001_current_schema.sql:523,3954`) — matching the stated "DB enforces invariants; app checks are the friendly first line" rule, not contradicting it.
- **The RLS-truth trap flagged in prior audits is already closed**, per the F7.4 evidence chain — this lane re-verified the baseline FORCE RLS count and the CI-role split rather than re-discovering a live gap.

## Unverified / needs judgment

- Is `public.auth_failure_counters.actor_id` (PERSIST-07) actually unique per tenant, or can the same actor_id span tenants such that a rate-limit counter leaks across tenant boundaries? Needs a read of the `actor_id` allocation scheme (tokens/iam), out of this lane's grep budget.
- How many of the 14 raw "query inside for-range" hits (PERSIST-08) beyond `release_coordinator.go` are genuine N+1 versus legitimate small bounded loops (e.g. per-table export/erasure loops in `tenant_data_port.go` files, which iterate over a fixed table list, not row-cardinality data)? This lane confirmed one, sampled two more as likely-benign, and left the rest unclassified.
- Does the taxonomy/iam second-BeginTx-port pattern (PERSIST-01) predate `db.TxRunner`, or was it added after and never migrated? No git-blame/history check was run — this lane reports the current-state duplication only, not its origin.
- Is `check-baseline-equivalence.ps1` (PERSIST-09) run manually before every baseline fold as an operator ritual (which would make the CI gap lower-severity), or is it aspirational tooling nobody runs? The docs cite it in planning/report files but this lane found no execution log or CI artifact confirming a run cadence.
