## The five heaviest, with detail

**HTTP-01 (6 error-emission mechanisms, 521 call sites).** Below ADR-0091's SurfacePublisher and ADR-0089's registry, the actual per-request act of writing an error is not standardized: 12+ locally-defined `writeProblem`/`WriteError` methods plus bare `httpErr`/`problem.Write` calls, each independently deciding how to serialize `*problem.Problem`. It multiplies the ADR-0089 `problem.New` vs `problem.NewFor` split (232/11, already known) by a second axis — even calls that pick the right code can still reach the wire through a different helper with different response-shape guarantees. Any future change to problem+json framing (headers, logging hook, trace-id injection) has 12+ places to touch, not one.

**HTTP-05 (0 spec-level runtime validation).** 123 OpenAPI constraints (`minLength`/`pattern`/`enum`) exist only as documentation; `kin-openapi` is wired for spec-serving, not for `openapi3filter.ValidateRequest`. Every one of those 123 rules is either re-implemented by hand somewhere in Go (duplicated, and possibly inconsistently) or not enforced at all except by a downstream DB constraint. This is the direct mechanism gap behind item 4 of the brief (validation lives wherever a human remembered to put it, contract-first in name only for validation).

**HTTP-06 / HTTP-07 (response-shape and header inconsistency).** Six modules share a generated `CursorPage` envelope; approval and templates diverge into `limit/offset`. Optimistic-concurrency (`If-Match`) exists only in approval — every other module's PATCH/PUT/DELETE-shaped mutation (documents rename, archive; taxonomy edits; template lifecycle transitions) has no equivalent stale-write guard, which is a hazard class, not just a style gap, and it is invisible from the outside because there is no cross-module response-shape check.

**HTTP-04 / HTTP-10 (generated types bypassed on both ends).** On the backend, 11 request bodies across 3 files are decoded into hand-typed anonymous structs instead of the oapi-codegen types the same route already has. On the frontend, `gen:api` produces a full generated type surface (8,362 lines) but only 4 files actually route requests through the paired `openapi-fetch` client; 18 feature files hand-declare their own response shapes. The generation pipeline exists on both sides of the wire and is only partially trusted on either side — contract-first is real for routing, only partial for payload shape.

**HTTP-08 / HTTP-11 (per-handler concerns re-solved per module).** Idempotency (already known to be intentionally per-handler, CLAUDE.md) has landed as 4 independent implementations rather than one reusable per-handler decorator — the "per-handler, not chain" design choice was correct, but each module then hand-built its own version of the same mechanism. Pagination-limit clamping shows the mirror problem: one shared helper (`pagination.ClampLimit`) exists, but it's invoked redundantly at both the HTTP and repository layer for the same request in several modules, meaning the boundary where the concern "belongs" was never settled.

## What is actually fine

- **Tier-2 capability assertion placement.** `authz.Require(` appears 32× in application/domain files vs 1× directly in a `delivery/http` file — matches the ADR-0022 invariant that capability checks live in-tx in the application service, not the handler. This is architecture working as designed, not a finding.
- **`pagination.ClampLimit`/`EncodeCursor`/`DecodeCursor` as a real shared platform helper** — it is a genuine single source of truth for cursor semantics (`internal/platform/pagination/cursor.go`), just over-called (HTTP-11) rather than duplicated in logic.
- **`tenant.FromContext` adoption for tenant extraction** — 30 call sites across the delivery layer use the one platform helper; unlike actor extraction (HTTP-12) there is no parallel hand-rolled tenant-extraction path found.
- **Approval module's post-remediation error registry** (`internal/modules/approval/http/errors.go`) — this module already did the ADR-0089 work: every problem code goes through `problem.Register`/`problem.RegisterWithStatus` with documented status-family reasoning (e.g. the 428-vs-412 distinction at `errors.go:70-72`). It's the one module that should be read as the target shape, not folded into the "6 mechanisms" finding as equally bad — its `WriteError`/`NewValidationError` pairing is internally consistent, just not shared outside the module.
- **Middleware chain composition itself** (`apps/api/cmd/metaldocs-api/chain.go`) — the 11-link chain is small, linear, and asserted by `chain_test.go` per the doc comment; nothing observed here contradicts REQ-MW-1..7. The gaps are what sits *below* the chain (per-handler idempotency, If-Match, admin-ctx), not the chain's own structure.

## Unverified / needs judgment

- Is `writeProblem`'s 186-call-site figure inflated by the fact `grep -F` counts both the 10 method *definitions'* internal bodies and call sites together for some files? Spot-checked 3 files and all matches were call sites, but the full 186 was not individually inspected — treat as an upper bound, order-of-magnitude confirmed.
- Whether the 4 modules with independent idempotency wiring (HTTP-08) actually differ in *semantics* (key derivation, TTL, conflict response) or only in *file organization* was not verified — only that they are structurally separate implementations with no shared helper.
- Whether `pagination.ClampLimit` being called at both HTTP and repository layer (HTTP-11) is redundant-but-harmless (same clamp applied twice, idempotent) or whether the two call sites in any single request path use different max values — not traced end-to-end for any one endpoint.
- Frontend hand-written `*Response` types (HTTP-10): whether these 18 files predate `gen:api`'s introduction (migration debt) or were added after it (active drift) was not determined — no git-blame/date correlation was run.
