## The five heaviest, with detail

**OBS-01/OBS-02 (worker & jobs binaries are observability-blind).** Half the running fleet — the async outbox consumer and the River scheduler/notifications binary — has no health endpoint, no metrics endpoint, and no compose healthcheck. `restart: unless-stopped` only catches a dead process, not a stalled poll loop or a wedged River client. This blocks any real SLA on outbox lag or job latency for those two binaries specifically, and blocks basic "is it actually working" verification without shelling into the container or reading raw stdout.

**OBS-07/OBS-08 (async trace is a string match, not a trace; logs need no context).** The `TraceID` persisted on outbox events is a bare string, never a W3C `SpanContext`, so a "failed background job" investigation is: read the API access log for the trace_id, grep worker stdout for the same string, hope both processes' JSON logs reached the same place. There is no automatic context→log bridge (no custom `slog.Handler`), so 79% of log call sites carry whatever fields the author remembered to add by hand. This is the same "hand-discipline instead of a mechanism" pattern the register catalogues elsewhere, applied to correlation fields.

**OBS-09/OBS-10 (error responses and error logs are structurally disconnected).** `writeProblem` never logs the condition it reports; only a panic guarantees a log line per request. A client-visible 500 and a server-visible log entry are two independent, uncorrelated artifacts unless the specific handler author chose to bridge them — which is inconsistent by construction across ~10 `writeProblem` copies and hundreds of call sites.

**OBS-05/OBS-06 (two metrics systems, one is fed lies).** Every HTTP request updates both a hand-rolled atomic-counter/percentile system and a real Prometheus registry, in the same function, by hand — a second system to keep numerically consistent with the first forever. Worse, the JSON system's business gauges (outbox depth) silently render `0` for a provider that has no DB handle, which is indistinguishable from "actually empty" without reading source.

**OBS-11/OBS-15 (jobs and alerting are entirely hand-inspected).** No scheduler-level log line exists independent of each job's own body, no River dashboard is vendored, and there are zero alert-rule definitions anywhere in the repository. Everything past "read `/metrics` in a browser" — dead-letter surfacing, job lag, outbox staleness — is a person running a query or reading stdout, not a firing mechanism.

## What is actually fine

- **Config surface is centralized and typed**, not scattered `os.Getenv`. All 23 files calling `os.Getenv` outside `main.go` live under `internal/platform/config/*.go`, one file per concern (`server.go`, `postgres.go`, `worker.go`, etc.), each exposing a `LoadXConfig() (XConfig, error)` with validation (e.g. `server.go:24-47` validates `APP_PORT`/`METRICS_ADDR` ranges before returning). This is the shape a remediation program should leave alone.
- **The metrics-listener isolation** (`/metrics` on a separate, non-host-published port) is a real, load-bearing security property, documented and tested — `ops/DEPLOY.md:154-174`, confirmed by `deploy/compose/docker-compose.yml` having no `ports:` mapping for the metrics port on `api`.
- **otelsql + otelhttp DB/HTTP-server instrumentation is real**, not decorative: `internal/platform/db/postgres/connect.go:36-45` wires every SQL call through `otelsql.Open`, and `OTelMiddleware` (`internal/platform/observability/otel.go:95-109`) wraps the server handler with bounded-cardinality span names. This is inert-by-default (env-gated, zero cost when OTel unconfigured) by explicit design (REQ-OBS-3) — that's a defensible engineering call, not an oversight.
- **No PII/secret leakage found in logs** — targeted searches for logged emails, tokens, passwords, and secrets in `slog.*` call sites returned zero hits.
- **Single logger, consistently configured**: `log/slog` is the only logging mechanism in production code (one `"log"` import, confined to the offline `metaldocs-e2e-seed` seed tool); all three binaries call `slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stdout, nil)))` identically, so structured JSON logging is uniform.
- **Readiness check is a real dependency probe**, not a stub, when DB-backed: `PostgresRuntimeStatusProvider.Ready` pings the DB with a 3s budget and runs pluggable `DependencyCheck`s concurrently under a 5s errgroup budget (`internal/platform/observability/runtime.go:116-153`) — reasonably deep for the one binary that has it.
