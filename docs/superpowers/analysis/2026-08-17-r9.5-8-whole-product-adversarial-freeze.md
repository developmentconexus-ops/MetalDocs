## 3. Candidate material findings / clarifications

These are the only material deltas produced by this pass. Everything else below is confirmation or an R10 proof obligation.

### F1 — Submission coherence invariant — CLARIFY, no reopen

A `RevisionSubmission` freezes one coherent governed state. Its primary Artifact, governed metadata and decision-relevant structured/template provenance MUST correspond to the same accepted `WorkingContent` version. They may not be independently snapshotted across concurrent DRAFT changes.

This is enforcement of the existing exact-Submission invariant, not a new object or workflow.

### F2 — `WorkingContent` is format-agnostic — CLARIFY, no reopen

`WorkingContent` is the mutable persisted authority of an open DRAFT Revision, independent of editor/provider/format.

Conceptually:

```text
WorkingContent
= current primary Artifact
+ governed metadata
+ optional structured authoring state
+ working_version
```

`structured_authoring` is absent when the chosen format/authoring model does not need it. EigenPal is one DOCX authoring provider around this state; it does not define `WorkingContent` semantics.

### F3 — external DRAFT replacement semantics — BOUNDED REOPEN of R9.5-3 only

The locked sentence that external download/edit/upload "fails on stale base" over-constrained product semantics by implying ancestry tracking between downloaded bytes and a later upload.

The required product behavior is simpler:

- while a Revision is `DRAFT`, any authorized actor may deliberately replace its current WorkingContent with supported content;
- every confirmed DRAFT mutation participates in the same `working_version` / OCC control, so two overlapping operations cannot silently last-write-win;
- after observing the newer DRAFT state, an authorized actor may deliberately retry a replacement;
- MetalDocs does not infer, track or require the ancestry of an arbitrary uploaded XLSX/DOCX/PDF from a prior download;
- `SUBMIT` freezes one exact coherent state into an immutable `RevisionSubmission`;
- once `SUBMITTED`, edit/upload/replacement of that attempt is rejected.

Therefore V1 does **not** need long checkout, download→upload lineage, an external-edit handle, binary merge, or semantic file comparison.

The bounded reopen affects only R9.5-3 external-edit stale-base semantics. Document/Revision/Submission/Approval/Release authority is unchanged.

### F4 — review-surface invariant — CLARIFY, no reopen

Approval review resolves only the exact `RevisionSubmission` being decided. Editors, viewers, previews and derived representations never become approval/content authority.

If a format/provider does not provide a sufficiently supported review representation, MetalDocs must fail closed to a supported inspection path for that same Submission, including exact-source download when appropriate. V1 does not promise a universal renderer or universal pixel-perfect preview.

### F5 — active LegalHold scope is prospective while active — CLARIFY, no reopen

A hold on stable `Document` or `Dossier` scope is not a one-time snapshot.

- when placed, it materializes the governed retention subjects currently in scope;
- while active, any newly created retention subject that enters that stable scope is also materialized into the held set;
- for a held Document, later submitted Revisions are held while the hold remains active;
- for a held Dossier, newly captured Evidence and newly linked governed subjects that enter the Dossier while the hold is active become held according to the same scope semantics;
- unlinking, archiving or later lifecycle changes do not release already-materialized held subjects;
- hold release is explicit and does not itself dispose content.

This preserves the existing meaning of a LegalHold over stable Document/Dossier scope without introducing eDiscovery/ESI capture.

### F6 — cross-scope links never become grants — CLARIFY, no reopen

- Dossier visibility does not grant Document visibility.
- Document visibility does not grant Dossier visibility.
- Dossier↔Document and secondary Evidence links are context relationships, not authorization edges.
- Search/timeline/projections must apply canonical authorization and may not expose hidden linked subjects.
- changing a DRAFT Evidence primary Dossier changes its derived scope and therefore requires authorization for both the current governed Evidence and the destination Dossier/scope; after CAPTURED the primary Dossier is immutable.
- creating a contextual link requires permission to manage the Dossier plus sufficient visibility to the linked governed subject; the link grants nothing afterward.

Strict Approval SoD from R9 remains unchanged.

### F7 — export completeness is explicit and fail-closed — CLARIFY, no reopen

A governed export cannot silently omit inaccessible related objects while claiming completeness. The eventual contract must either explicitly define a bounded subject-only/reference-only package or fail when the requested completeness cannot be authorized. Export never grants read access and never changes retention/hold state.

## 5. Bounded R9 authorization delta

### 5.1 Operations first

R9.5 adds these material business operations:

**EvidenceType**
- manage tenant-scoped EvidenceType definition, allowed formats, naming and retention policy.

**Evidence**
- read governed Evidence;
- create DRAFT Evidence;
- edit/replace DRAFT Evidence;
- CAPTURE Evidence;
- VOID invalid MetalDocs capture.

- manage tenant-scoped DossierType definition and eligible types.

**Dossier**
- read;
- create;

- lengthen a RetentionBinding;
- place/release/manage LegalHold;

- governed-subject package export needs an explicit capability distinct from existing `tenant.export` and `audit.export`;

## 7. R10 proof obligations — not R9.5 semantic reopens

If R9.5 freezes, R10 must make these properties mechanically provable:

1. atomic/coherent creation of `RevisionSubmission` from one accepted WorkingContent version;
2. one OCC guard across every DRAFT-mutating path and the DRAFT→SUBMITTED transition;
3. late autosave/upload cannot mutate a SUBMITTED Revision;
4. release is idempotent/atomic and preserves exactly-one-EFFECTIVE-revision;
5. required Rendition failure blocks release without invalidating Approval;
6. Managed Artifact confirmation occurs only after required validation/integrity checks; failed/stale staging becomes GC data, not orphan authority;
7. provider relocation keeps old location authoritative until exact-byte/hash verification and cutover complete;
8. active LegalHold materialization catches newly entering retention subjects and unlink/lifecycle changes cannot escape already-held subjects;
9. disposition records completion only after verified physical removal of the governed retention unit and no active hold;
10. tenant erasure rechecks retention/hold blockers and backup/restore reapplies tombstones before service/cleanup resumes;
11. cross-scope query/search/timeline/export surfaces fail closed and never use contextual links as grants;
12. historical migration is idempotent/reconcilable per semantic unit and never fabricates unknown source truth;
13. external publish/job retries are idempotent and never report an external effect that did not succeed;
14. export completeness contract is explicit and authorization-safe.

These belong to bounded contexts/data model/transactions/events/API technical design in R10. They do not justify adding new R9.5 domain concepts now.

## 9. External-reference sanity checks — evidence, never target authority

These references were used only to challenge mechanism assumptions:

- Microsoft Graph `DriveItem` update documents conditional writes using `If-Match`/eTag and returns `412 Precondition Failed` on mismatch. This supports OCC as a standard mechanism, but MetalDocs product semantics do not adopt provider identity or file ancestry.
- Amazon S3 `CopyObject` exposes checksum support. MetalDocs still verifies its own canonical SHA-256 because provider checksums/location/version IDs are mechanisms, not Artifact business identity.
- Microsoft Purview retention documentation shows retention/hold implementations preserving content even when users edit/delete it and applying retention to content created after a policy includes a site. This is a sanity check for prospective preservation semantics, not a source of MetalDocs legal policy.
