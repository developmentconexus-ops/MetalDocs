## 1. Global-maximum judgment (carried from P0 §2)

The legacy role-based template-approval path is a **named local maximum**: a second, parallel approval implementation that ADR 0072 explicitly warned against and ADR 0082 ratified for retirement. The global maximum is **kernel-only** — one subject-discriminated approval implementation (`internal/modules/approval`) serving both `documents` and `templates`. This unit **deletes** the local maximum; it does not optimize inside it. No competing structure exists → no GM fork.

## 2. Why the sequence is mandatory (a) → (b) → (c)

`templates_approval_config` + `domain.ApprovalConfig` + the role fields are shared between the 4 legacy routes AND two non-legacy callers (`CreateTemplate` seeds roles + writes the config table; `PublishTemplateVersion` does role-SoD). Therefore:

- **(a) first** — migrate `CreateTemplate` (stop seeding roles) + `PublishTemplateVersion` (kernel-conformant completion, drop role-SoD) off the role model. Until this lands, the table/type are load-bearing and cannot be dropped.
- **(b) second** — rebuild the FE onto the kernel routes (`/submit-for-approval` + `/signoff`). The legacy backend routes must stay live until the FE no longer calls them, or the UI 404s.
- **(c) last** — delete the legacy backend path (routes + handlers + service methods + domain + repo methods + tests) and DROP the table behind a pre-drop emptiness assert; clean up `CapTemplateReview` + `domain.ApprovalConfig` orphans.

Reversing the order strands create/publish (drop-first) or 404s the UI (delete-routes-first).

## 7. Inventory / deletion-target map (APPENDIX — from INV-1: 2 sonnet investigators, reports consistent)

### 7.1 Risk resolutions
- **R1 RESOLVED (publish SoD):** `lifecycle.go:420-427` = two gates. (1) `CheckSegregation(SegregationRoleApprover, actor, author, reviewer)` @421 = **identity**-SoD (user IDs, not roles) — ISO "no self-publish". **KEEP.** (2) `RoleBindingFor(Published)` + `containsRole(cmd.ActorRoles,…)` → `ErrForbiddenRole` @424-427/450 = role-model authz. **REMOVE** — this is the ratified "drop role-SoD". "Kernel-driven" additionally means publish completes kernel-approved versions: verify/extend status gate for `approved → published` (legacy `Approve` owned that transition; after S4 deletion the kernel flow would dead-end at `approved` without it). `CanTransition` already contains approved→published.
- **R2 RESOLVED (tripwire):** `template.review` is NOT load-bearing for any kept `templates_template_version` write — kernel submit asserts `template.submit` (`template_submit_service.go:144`), kernel signoff asserts `template.approve` (`decision_service.go:325-329`, subject-discriminated), publish asserts `template.publish` (`lifecycle.go:479`). Removal safe. BUT deleting the Go const forces `arms.go:232` edit (arm #14) → GMR-M2 arms↔SQL parity lint requires re-rendering `enforce_capability_asserted()` via the registry path (`render.go`) into its OWN forward migration (M2 protocol: never hand-edit, never bundle).
- **R4 RESOLVED (shared components):** legacy-exclusive schemas deletable: `TemplateVersionEnvelope` (~6394), `ApproveTemplateVersionResponse` (~6384), `TemplateApprovalConfig` (~6417), `UpsertTemplateApprovalConfigResponse` (~6424). ⚠ `VersionDTO` (~6315) SHARED with kept ops — NOT deletable (only loses its two pending-role fields in S4). `CreateTemplateRequest` carries `approver_role`/`reviewer_role` (~1266-1267); FE never sends them → removed in S1.
- **NEW RISK (GDPR erasure):** `infrastructure/tenant_data_port.go:76-79` `EraseTenantData` raw-DELETEs `templates_approval_config` → MUST be edited in the SAME change as the DROP migration or tenant erasure breaks at runtime.
