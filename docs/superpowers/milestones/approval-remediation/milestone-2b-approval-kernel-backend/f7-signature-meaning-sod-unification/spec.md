| 1 | Does `domain.CheckSoD` already exist, or does F7 need to create it? | It already exists (`internal/modules/documents/approval/domain/sod.go`, presumably landed with an earlier feature's schema/domain groundwork) — `CheckSoD(authorUserID, actorUserID string, priorSignoffs []Signoff) error`, returning `ErrAuthorCannotSign` on self-sign and `ErrActorAlreadySigned` on cross-stage re-sign. `decision_service.go`'s signoff path already calls it (`decision_service.go:301`, `domain.CheckSoD(instance.SubmittedBy, req.ActorUserID, priorSignoffs)`). F7's SoD job is NOT "create the primitive" — F4 already did that, and F4's own evidence.md flagged the gap: `review_verdict_service.go` (F4) implements the identical self-verdict rule **inline** (`if instance.SubmittedBy == req.ActorUserID { return domain.ErrAuthorCannotSign }`, line 151-153) instead of calling `CheckSoD`, a documented deviation deferred explicitly "revisit alongside F7 (SoD unification)". F7's job is to collapse this duplication: make `review_verdict_service.go` call the same `CheckSoD` function `decision_service.go` calls. |
| 2 | Does `CheckSoD`'s `priorSignoffs []Signoff` parameter fit the review-verdict call site as-is, or does it need a signature change? | It fits with `nil`. The `priorSignoffs` parameter enforces "actor cannot sign twice across stages of the same instance" — a rule that requires a same-shape prior-record lookup (`LoadPriorSignoffs`, which queries `approval_signoffs` specifically). Review verdicts live in a structurally different table (`approval_review_verdicts`, migration 0288) with a different per-stage-actor uniqueness constraint already enforced at insert time (`UNIQUE(stage_instance_id, actor_user_id)`, `InsertVerdict`'s `ON CONFLICT ... DO NOTHING` + replay-vs-conflict detection in F4). Spec.md's SoD rule (§5, W7) for review verdicts is exactly "reviewer may be anyone but author self-verdict blocked" — it does NOT ask for a cross-stage-reuse rule for verdicts. Passing `nil` for `priorSignoffs` reuses `CheckSoD` for exactly the sub-rule review verdicts need (self-sign check) without fabricating a `[]Signoff` slice from unrelated `ReviewVerdict` rows (which was F4's own stated reason for NOT doing this at the time — a `nil` slice sidesteps that adapter-shape problem entirely, since `CheckSoD`'s loop over `priorSignoffs` is a no-op on `nil`). This is not a signature change to `CheckSoD` — `domain/sod.go` stays untouched at the Go level (verified: the plan.md file list only lists it as "modified" for the doc-comment describing the now-shared reuse, not a parameter change). |
| 3 | Is there a second DB-level enforcement site for review verdicts, mirroring `trg_signoff_sod` on `approval_signoffs`? | No. Grep of `db/baseline/0001_current_schema.sql` and all migrations through 0288 confirms exactly ONE SoD trigger exists: `enforce_signoff_sod()` / `trg_signoff_sod BEFORE INSERT ON approval_signoffs`. `approval_review_verdicts` (new table, migration 0288) has no equivalent trigger — F4's own evidence.md acknowledged the parallel gap for the tripwire-arm registry but did not address SoD-trigger parity, and plan.md's F7 file list explicitly calls for `0290_sod_unified_trigger.sql` to "collapse the app+trigger duplication" — read literally this assumes today's state is "duplicated trigger + duplicated app check" (i.e., two triggers), which is not what the codebase shows: today there is ONE trigger (signoffs only) and TWO app-level checks (signoffs via `CheckSoD`, verdicts inline). The actual defect to fix is: (a) app-level duplication (per #1/#2 above) and (b) missing DB-tripwire parity for the newer table (verdicts have zero DB-level SoD enforcement — a real gap, not a duplication, but the same underlying principle: app-checks-first + DB-tripwire-last on EVERY mutating table that records a self-sign-capable decision). F7 implements ONE shared SQL function (mirroring `enforce_signoff_sod`'s exact rule text and error message convention) and attaches it via two triggers — one on `approval_signoffs` (already exists, left as-is or re-pointed to the shared function for DRY) and one new one on `approval_review_verdicts`. This satisfies plan.md's literal ask ("ONE trigger calling one SQL function whose rule text mirrors `ViolatesSoD`") in spirit: one function, attached wherever a self-sign-capable row is inserted. |
| 4 | Plan.md names the unified predicate `domain.sod.go — single exported predicate ViolatesSoD(authorID, actorID, stageKind)`. Does F7 rename `CheckSoD` to `ViolatesSoD`, or keep `CheckSoD`? | Keep `CheckSoD`. Plan.md's exact function name/signature is illustrative ("plan.md's file list... adapt to real code, not assume" — same runtime-truth caveat plan.md states at the top for every feature, confirmed by F1-F6's own precedent of adapting exact names to what already exists). Renaming a widely-called, already-shipped, already-tested function (`decision_service.go`, `decision_service_test.go`, `sod_test.go`, `errors.go`'s mapping via `errors.Is(err, domain.ErrAuthorCannotSign)`) for a cosmetic rename is a pure refactor with no behavior change and a large, out-of-proportion blast radius for this feature's actual bug (the duplication). Global-maximum judgment: the "single exported predicate" requirement is satisfied by `CheckSoD` already being that predicate — the defect is that `review_verdict_service.go` doesn't call it, not that its name doesn't match plan.md's placeholder. `stageKind` is likewise not added as a parameter: spec.md §5 states the SoD rule text is identical regardless of stage kind ("author ≠ approver on same instance; reviewer may be anyone but author self-verdict blocked" — both clauses are the SAME "author cannot act on their own submission" rule, stage-kind-agnostic), so a `stageKind` parameter would be dead weight with no rule branching on it. |
| 5 | What exactly does "signature meaning" (W8, 21 CFR 11.50(a)(3)) need, given `signature_meaning` is already a column (migration 0286) and already round-trips through the repository (`InsertSignoff`/`LoadSignoffByActor`/`LoadPriorSignoffs`/`LoadStageSignoffs`/batch-load, all already SELECT/INSERT `signature_meaning`) and the domain (`domain/signoff.go`'s `SignatureMeaning()` getter, `SignoffParams.SignatureMeaning`, defaults to `"approval"` when unset)? | The ONE missing wire is: **`decision_service.go`'s `RecordSignoff` never sets `SignatureMeaning` when constructing the domain `Signoff`** (`decision_service.go:308-321`'s `domain.NewSignoff(domain.SignoffParams{...})` call has no `SignatureMeaning` field set at all). Because `NewSignoff` defaults an empty `SignatureMeaning` to `"approval"` (`signoff.go:130-132`), every signoff — including REJECT decisions — is persisted with `signature_meaning = 'approval'`. This is exactly the class of defect 21 CFR 11.50(a)(3) exists to prevent: the persisted record must state what the signature actually means, and "this rejection means approval" is a false attestation on every reject signoff shipped since migration 0286 landed. The fix: `RecordSignoff` derives `SignatureMeaning` from `req.Decision` — `DecisionApprove → "approval"`, `DecisionReject → "rejection"` (the two enum values the CHECK constraint and `NewSignoff`'s own validation already admit; no new vocabulary term is introduced, matching plan.md's contract note "enum `[approval, rejection]`; server-derived from decision"). |
| 6 | Is `signature_meaning` exposed anywhere in the actual live HTTP response today (not just the openapi schema)? | No — checked both. (a) The mutation response (`POST .../signoff`, both instance-scoped and by-document variants) returns `contracts.SignoffResponse{signoff_id, was_replay, outcome}` (`http/contracts/signoff.go`) — this response shape never carried per-signoff decision detail at all (not even `decision` itself), so it is not the natural home for `signature_meaning` and plan.md does not ask for it there. (b) The read/manifest path — `GET /approval/instances/{id}` and `GET /documents/{id}/approval-instance`, both served by the SAME hand-maintained `contracts.InstanceResponse`/`contracts.SignoffRecord` (`http/contracts/instance_read.go`, built by `mapInstanceResponse` in `get_instance_handler.go`) — is the actual "signature manifest" spec.md §2.1 means ("rendered in the signature manifest and audit trail"). `contracts.SignoffRecord` today has `{ID, ActorUserID, Decision, Reason, SignatureMethod, SignedAt}` — no `signature_meaning` field, and `mapInstanceResponse`'s per-signoff loop (`get_instance_handler.go:69-76`) never reads `sig.SignatureMeaning()` even though the domain getter already exists. This IS the actual openapi contract-touching part of F7: the `api/openapi/v1/openapi.yaml` schema most directly named by plan.md (`ApprovalSignoffRecordResponse`, embedded in `ApprovalInstanceByDocumentResponse`) is a DIFFERENT, currently-dead-at-runtime generated schema (confirmed: grep shows zero Go call sites constructing `approvalapi.ApprovalSignoffRecordResponse{}` anywhere in `internal/modules/documents/approval` — `GetInstanceHandler`/`GetInstanceByDocumentHandler` both return the hand-maintained `contracts.InstanceResponse` instead, an existing hand-rolled-vs-generated-contract split that predates F7 and is out of this feature's scope to reconcile). F7 extends the LIVE contract (`contracts.SignoffRecord` + its openapi-adjacent hand doc, since this endpoint's actual wire shape is not one of the generated schemas) rather than a schema with no runtime reader. The pre-existing openapi/generated-vs-hand-rolled split for this endpoint is noted as an out-of-scope observation, not fixed here (see Non-goals). |
| 7 | Does the request side (`SignoffApprovalStageRequest`/`SignoffDocumentRequest` in openapi, `contracts.SignoffRequest` in Go) need a new `signature_meaning` input field? | No — per plan.md: "signoff request/response gain `signature_meaning`... **server-derived from decision**". The client never chooses the meaning; the server derives it deterministically from the `decision` field the client already sends (approve/reject), exactly like `contentHash`/`signature_method` are server-controlled today. Adding a client-writable `signature_meaning` request field would open a spoofing surface for a Part-11 attestation field — the opposite of the design intent. Confirmed no such client input exists in any of spec.md/plan.md's wording; only "expose in signoff DTO + manifest" (i.e. response-side only). |
| 8 | Does `ReviewVerdict` (F4, no e-signature semantics) need a `signature_meaning`? | No. Spec.md §2.1 is explicit: review-stage verdicts are "No password re-auth — review is not a signature event." `signature_meaning`/21 CFR 11.50(a)(3) is a signature-record concept; `approval_review_verdicts` has no `signature_method`/`signature_payload`/`content_hash` columns either (F4's migration 0288 comment: "no e-signature semantics for review-stage feedback, unlike binding approval signoffs"). Confirmed out of scope by symmetry with F4's own explicit non-goal framing — not revisited here. |

## Consumer contract

**SoD unification** (`internal/modules/documents/approval/application/review_verdict_service.go`, `internal/modules/documents/approval/domain/sod.go`):

- `review_verdict_service.go`'s inline self-verdict check (lines 146-153: `if instance.SubmittedBy == req.ActorUserID { return domain.ErrAuthorCannotSign }`) is replaced with a call to the SAME `domain.CheckSoD(instance.SubmittedBy, req.ActorUserID, nil)` that `decision_service.go` calls (`nil` for `priorSignoffs` — see Interview #2; the cross-stage-reuse clause is a no-op against `nil` and does not apply to the verdict shape). Both callers now execute the identical code path for the "author cannot act on their own submission" rule — grep-zero for the old inline `SubmittedBy ==` pattern proves the duplication is gone (both signoff and verdict recording call through one function).
- `domain/sod.go`'s doc comment on `CheckSoD` is updated to state explicitly that both `RecordSignoff` (approval-stage) and `RecordVerdict` (review-stage) call this single predicate — making the "single exported predicate" property self-documenting at the source, matching plan.md's intent without a rename (Interview #4).
- New migration `db/migrations/0290_sod_unified_trigger.sql`: extracts the existing `enforce_signoff_sod()` function body into a shared, table-agnostic form (reads `author_id` via `approval_instances.document_id → documents.created_by`, exactly like today, keyed off `NEW.approval_instance_id` — a column both `approval_signoffs` and `approval_review_verdicts` already have) and attaches it as a BEFORE INSERT trigger to BOTH `approval_signoffs` (existing table — re-pointing its trigger to the shared function, no behavior change, same error message/ERRCODE) and `approval_review_verdicts` (new trigger — the previously-missing DB-tripwire-last line of defense for verdict self-recording, closing the gap Interview #3 identifies).

**Signature meaning** (`internal/modules/documents/approval/application/decision_service.go`, `internal/modules/documents/approval/http/contracts/instance_read.go`, `internal/modules/documents/approval/http/get_instance_handler.go`, `api/openapi/v1/openapi.yaml`):

- `decision_service.go`'s `RecordSignoff` derives `signatureMeaning` from `req.Decision` immediately before constructing `domain.NewSignoff(...)`: `domain.DecisionApprove → "approval"`, `domain.DecisionReject → "rejection"`, and passes it as `SignatureMeaning: signatureMeaning` in `SignoffParams`. This is the one missing wire — every downstream layer (domain validation, repository persistence, repository reads) already round-trips the field correctly once it is set at construction time.
- `contracts.SignoffRecord` (`http/contracts/instance_read.go`) gains a `SignatureMeaning string \`json:"signature_meaning"\`` field.
- `mapInstanceResponse`'s per-signoff loop (`get_instance_handler.go`) adds `SignatureMeaning: sig.SignatureMeaning()` to the constructed `contracts.SignoffRecord{}` literal — the manifest now renders the actual attestation meaning per spec.md §2.1.
- `api/openapi/v1/openapi.yaml`'s `ApprovalSignoffRecordResponse` schema (the nearest-named schema to this concept, even though not the schema this specific hand-maintained endpoint returns — see Interview #6) gains a `signature_meaning: {type: string, enum: [approval, rejection]}` property, keeping the documented contract surface in sync with the domain vocabulary for any future consumer of the generated schema, and satisfying plan.md's explicit "Modify: `api/openapi/v1/openapi.yaml` — signoff request/response gain `signature_meaning`" file-list line. `oapi-codegen` regen follows (no handler code changes result, since no live handler currently constructs this generated type — see Non-goals).

## Non-goals

- **Renaming `CheckSoD` to `ViolatesSoD` or adding a `stageKind` parameter** — see Interview #4. The existing name/signature already satisfies the "single exported predicate" requirement; a rename is pure refactor churn with no functional benefit and risks breaking `errors.Is`-based call sites and existing green tests for no gain.
- **Reconciling the openapi-generated `ApprovalSignoffRecordResponse` schema with the hand-maintained `contracts.SignoffRecord` DTO actually used by `GetInstanceHandler`/`GetInstanceByDocumentHandler`** — this pre-existing generated-vs-hand-rolled split (Interview #6) is a real observation but out of F7's file-list scope (plan.md names `signoff.go`, `decision_service.go`, `postgres_approval_repository.go`, `domain/sod.go`, the 0290 migration, and openapi — not a rewrite of the instance-read handler's DTO strategy). F7 updates the openapi schema for contract-surface completeness and updates the LIVE DTO (`contracts.SignoffRecord`) separately, since that is the one actually rendered to a client; it does not migrate the handler onto the generated type. Flagged as a candidate for a future dedicated cleanup task.
- **Adding `signature_meaning` to `ReviewVerdict`/`approval_review_verdicts`** — see Interview #8; review verdicts have no signature semantics by design (F4/spec.md non-goal), unchanged here.
- **A client-writable `signature_meaning` request field** — see Interview #7; server-derived only, no new request-body property, no new client input validation.
- **Changing `CheckSoD`'s cross-stage re-sign behavior (`ErrActorAlreadySigned`) for review verdicts** — `InsertVerdict`'s existing `ON CONFLICT (stage_instance_id, actor_user_id) DO NOTHING` + replay-vs-conflict detection already handles "same actor, same stage" idempotently (F4); passing `nil` priorSignoffs to `CheckSoD` from the verdict path means the cross-stage clause simply never fires for verdicts (there is no rule in spec.md asking for it) — this is intentional, not a regression, per Interview #2.
- **Any change to the F5/F6 hash-chain, freeze boundary, or F8/F9 SLA/delegation/visibility work** — F7's file list and this spec are scoped exactly to W7 (SoD unification) and W8 (signature meaning), per plan.md's feature boundary.
