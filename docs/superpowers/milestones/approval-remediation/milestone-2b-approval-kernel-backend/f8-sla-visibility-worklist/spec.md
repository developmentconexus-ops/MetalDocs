## Interview record (self-directed, no operator ambiguity requiring a stop)

| # | Question | Answer |
|---|----------|--------|
| 1 | Is there an existing `due_in_days`/`due_at` mechanism to reuse, or must F8 build one? | `stage_kind`/`due_in_days`/`due_at` columns and the corresponding Go fields (`domain.RouteStage.DueInDays`, `domain.StageInstance.DueAt`) were already added by F1's schema-expand migration `0286` and are already SELECTed by `postgres_approval_repository.go` (`LoadInstance`/`LoadInstancesByIDs` queries at lines 643/704 and 884/941 both read `stage_kind, due_at` into `s.DueAt`). But NOTHING ever WRITES `due_at`: `InsertStageInstances` (repository, lines 68-129) has a fixed 14-column INSERT that does not include `due_at` at all, and `UpdateStageStatus`'s activation `CASE` only sets `opened_at = now()` on activation — no `due_at` computation anywhere. `submit_service.go`'s stage-instance construction loop (lines 194-229) never reads `stage.DueInDays` or sets `StageInstance.DueAt`. This is the exact, verifiable gap F8 closes — not a second parallel mechanism, since the columns/fields are already the single source; F8 wires the write side only. |
| 2 | Is this the same due-date mechanism as `document_review_surfacer` (GMR M6, periodic eQMS document review)? | No — verified by reading `internal/modules/jobs/document_review_surfacer/job.go` and `internal/modules/jobs/maintenance/periodic.go`. That job surfaces `documents.review_due_at`/`review_surfaced_at` (a document-level periodic-review cadence, e.g. "re-review this SOP every 2 years") via the `documents` module's own `ReviewDueReader`/`ReviewSurfaceWriter` ports — semantically unrelated to an in-flight approval stage's SLA clock (`approval_stage_instances.due_at`, "this reviewer has N days to act on this specific stage instance"). Building approval-stage SLA surfacing as a literal extension of `document_review_surfacer` would conflate two different due-date concepts on one job/table pair — a real column/job reuse-across-unrelated-purposes risk (the F4 caught-bug class CLAUDE.md calls out). Per plan.md's own wording ("extend `document-review-surfacer` (or **sibling** periodic job, same pattern)"), F8 builds a **new sibling job** — `approval_sla_surfacer` — that follows the identical structural pattern (dual-phase tenant enumeration + per-tenant seeded tx, alert-only, ADR 0068 philosophy, River `maintenance` queue, dual-defined in `jobs/maintenance/periodic.go` per ADR 0067) but reads/writes only `documents/approval`-owned ports and rows. This satisfies the orientation-rule instruction to reuse the pattern without forking the *table* or *port*. |
| 3 | What does "SLA" concretely compute, and where does `due_in_days` come from? | `due_in_days` is a per-route-stage config value (`approval_route_stages.due_in_days`, nullable — optional per spec §4). At the moment a stage becomes `active` (both at submit, for the first stage, and at stage-advance, for every subsequent stage), if the newly-activated stage's `DueInDaysSnapshot` is non-nil, `due_at = opened_at + due_in_days days` is computed and persisted; if nil, `due_at` stays NULL (no SLA configured for that stage — never defaulted to some fallback value, consistent with the no-fallback principle's spirit of not inventing substitute values for an intentionally-absent config). This requires snapshotting `due_in_days` from the route stage onto the stage-instance row at submit time (mirroring how `NameSnapshot`/`RequiredRoleSnapshot`/etc. already snapshot other route-stage config) — F1 did not add a `DueInDaysSnapshot` field to `domain.StageInstance` (only `DueAt` exists), so F8 adds it. |
| 4 | Does `AdvanceStage()` (domain, pure function) compute `due_at` itself, or does the caller? | The caller (application-layer service), same division of labor as `OpenedAt`: `AdvanceStage()` already sets `OpenedAt = &now` on the newly-activated stage in memory (domain/instance.go:121) but the actual DB write of `opened_at` happens in the repository's `UpdateStageStatus` SQL (`CASE WHEN $1='active' THEN now()`), not by trusting the in-memory value — the DB computes its own `now()` as the authoritative timestamp. F8 follows the same pattern: extend `UpdateStageStatus` (or add a sibling method) to also accept and persist `due_at` computed from the snapshot at the SQL layer (`now() + (due_in_days_snapshot || ' days')::interval`), so the DB's own clock is the single source of truth for both `opened_at` and the derived `due_at`, avoiding any app-clock/DB-clock skew between the two. This requires `due_in_days_snapshot` to also be a column on `approval_stage_instances` (new, F8-owned) so the activation UPDATE can read it without a second round-trip to `approval_route_stages` (which may have moved to a new route version by then — F2 versioning). |
| 5 | Visibility gating (P2/P3/P8): what exactly is the new rule, and does it conflict with existing tested behavior? | Yes — real conflict, resolved as an intentional tightening, not silently patched. `read_service_tenant_grade_view_integration_test.go` (pre-existing, labeled "F0.3") deliberately made `CapDocumentView` (tenant-grade, `ScopeTenant` in `capability_scope.go:54`) sufficient on its own for `LoadInstance`/`LoadActiveInstanceByDocument` to return ANY in-flight instance in the tenant, regardless of area — this is today's actual, tested "consumer contract". Design spec.md §6.3 (ratified) narrows this: **consumers** (any actor whose only grant is view-only `document.view`) must see ONLY the published/effective revision — an in-flight/unpublished instance's detail is a 404 to them, not visible via bare `document.view`. Only {author (`inst.SubmittedBy`), a stage pool member on any current-or-past stage (`EligibleActorIDs` across `inst.Stages`), `approval.oversee` holders, `document.edit` holders} may see the in-flight instance. This is a deliberate, spec-ratified supersession of the F0.3 tenant-grade-view behavior for *in-flight instance detail specifically* — F0.3's test file is updated in place (not deleted; its system_admin-bypass and no-grant-denied cases are still correct and kept, only the "bare document.view is sufficient" assertions are replaced with the new eligibility∪oversee∪edit rule). This is exactly the P2/P3/P8 gap the whole M2b program exists to close (spec.md's own framing: "Two-tier PDP... visibility gating... a reviewer sees only instances/stages where they hold the relevant capability" — the old F0.3 shape was the pre-remediation gap being fixed, not a competing correct design). |
| 6 | Consumer-denied-visibility must be 404, not 403 (spec §6.3 "cross-boundary = not-found") — how, given `authz.ErrCapDenied` maps to 403 today (`http/errors.go:273-275`)? | A new sentinel, `infrastructure.ErrInstanceNotVisible`, distinct from both `ErrNoActiveInstance` (row genuinely absent/wrong tenant) and `authz.ErrCapDenied` (used for the "actor holds ZERO relevant capability at all, including no `document.view`" case, which stays 403 — an actor with literally no view-family grant is a true authz-forbidden case, not a visibility-eligibility case). `ErrInstanceNotVisible` is returned by the read-service visibility predicate when the actor DOES hold `document.view` (tenant-grade — passes the existing `authz.Require` gate, so it is "in the building") but is not in the eligibility set for this SPECIFIC instance and holds neither `document.edit` nor `approval.oversee`. It maps to `http.StatusNotFound` in `errors.go`, same status as `ErrNoActiveInstance`, deliberately indistinguishable on the wire from "doesn't exist" (spec.md §6.3's literal "cross-boundary = not-found, consistent with the tenancy rule" — a consumer must not be able to distinguish "no such instance" from "an instance exists here but you can't see it", which would itself leak information). |
| 7 | Does the visibility predicate apply to `LoadActiveInstanceByDocument` too, or only `LoadInstance`? | Both — spec.md §6.3 talks about "instances, and cockpit URLs" generically, and `LoadActiveInstanceByDocument` is the read path the FE cockpit/document-view page calls to decide whether to show the "Em aprovação/revisão" badge and in-flight detail; it is exactly as visibility-sensitive as `LoadInstance`. Both methods get the same new predicate, sharing one unexported helper function so the rule is defined once (mirrors F7's single-predicate discipline for SoD). `LoadActiveInstanceByDocumentForMutation` (used by mutation services which enforce their own capability gates) is explicitly UNCHANGED — spec.md's visibility rule is a read-path/display concern, not a mutation-authorization concern, and this method's doc comment already states mutation services gate themselves. |
| 8 | Post-publication approval history (spec §6.3 "visible to any actor who can view the document") — does this need a separate code path? | No new code path: once an instance transitions to a terminal `approved` status and the document is published, ordinary `document.view` continues to work for the *document* itself (unaffected, outside approval module scope) and the approval *history* read (if/when a dedicated "approval history" endpoint exists) is out of scope for F8 — grep of the current routes shows no separate historical-instances-list endpoint exists yet; `GetInstanceHandler`/`GetInstanceByDocumentHandler` are the only instance-detail reads, and the new predicate naturally satisfies "post-publication visible to any viewer" because `InstanceApproved` is the intended terminal end-state most consumers would encounter navigating from the published document — however, per spec.md's literal rule (view = eligibility ∪ oversee ∪ edit, no "if terminal, open to all" carve-out is stated), F8 does NOT add a status-based carve-out that would let a bare consumer see a *terminal* instance's stage-by-stage signoff detail either; this is flagged as a bounded defer (a real ambiguity between spec.md §2.2/§6.1's "post-publication approval history visible to any actor who can view the document" bullet and §6.3's stricter enumerated list) rather than guessed silently. |
| 9 | Worklist: is `/approvals` (M2c FE destination) or the existing `/approval/inbox` (`InboxHandler`) the F8 surface? | `/approval/inbox` (existing, `inbox_handler.go`/`ReadService.ListInboxItemsWithTotal`) is the ONLY backend worklist endpoint that exists today; `/approvals` is an M2c (frontend, not this milestone) route that will consume this same backend endpoint. F8 extends the existing inbox query/handler/DTO rather than inventing a parallel endpoint — plan.md's "Modify: inbox/worklist handler+service" file-list line names exactly this file. The inbox query ALREADY scopes visibility correctly at the SQL layer today (`asi.eligible_actor_ids @> $2::jsonb` — actor must be in the pool; this is real query-layer gating, not a client-side filter) — F8 does not touch that base-eligibility predicate; it ADDS the stage_kind/due_before filters and the oversee variant on top of the existing, already-correct eligibility scoping. |
| 10 | What does `?scope=oversee` mean for the worklist, precisely? | When the caller holds `CapApprovalOversee` and passes `scope=oversee`, the query drops the `eligible_actor_ids @> actor` predicate entirely and returns ALL in-progress instances tenant-wide (still `tenant_id = $1`-scoped — never cross-tenant), matching spec.md §6.1's "read-only oversight of ANY instance in tenant". Without the query param (default), behavior is unchanged: eligibility-scoped to the caller. Requesting `scope=oversee` without holding `CapApprovalOversee` is a 403 (`authz.ErrCapDenied` — this is a deliberate action gate, not a visibility-leak case, so 403 is correct here per spec.md's existing capability-check convention, distinct from Interview #6's instance-detail 404 case which is about an already-authenticated document.view holder probing a specific instance they're not eligible for). |

## Consumer contract

### SLA (W4)

- `internal/modules/documents/approval/domain/route.go`: no change needed (`StageDefinition.DueInDays *int` already exists per F1).
- `internal/modules/documents/approval/domain/instance.go`: `StageInstance` gains `DueInDaysSnapshot *int` (new field, alongside the existing `DueAt *time.Time`). `AdvanceStage()` stays a pure in-memory transition function (unchanged signature) — it does not compute `DueAt` itself; the DB remains the authoritative clock (Interview #4).
- `db/migrations/0292_approval_stage_sla.sql` (new): `ALTER TABLE approval_stage_instances ADD COLUMN due_in_days_snapshot integer NULL CHECK (due_in_days_snapshot IS NULL OR due_in_days_snapshot > 0);` — snapshot column so activation UPDATEs never need a second read against a possibly-superseded route version (F2).
- `internal/modules/documents/approval/infrastructure/postgres_approval_repository.go`:
  - `InsertStageInstances`: adds `due_in_days_snapshot` to the fixed column list, sourced from `StageInstance.DueInDaysSnapshot`.
  - `UpdateStageStatus`: when `newStatus == StageActive`, also sets `due_at = CASE WHEN due_in_days_snapshot IS NOT NULL THEN now() + (due_in_days_snapshot || ' days')::interval ELSE NULL END` in the same UPDATE (DB-computed, no app-clock dependency).
  - `LoadInstance`/`LoadInstancesByIDs`: unchanged (already SELECT `due_at`); additionally SELECT `due_in_days_snapshot` into the new domain field so it round-trips (needed for any downstream re-activation, e.g. none currently re-activates a stage, but keeps the snapshot available for display/debugging).
- `internal/modules/documents/approval/application/submit_service.go`: the stage-instance construction loop sets `DueInDaysSnapshot: stage.DueInDays` for every stage (not just the first) so every stage's SLA config is captured at submit regardless of when it later activates.
- New sibling River periodic job `internal/modules/jobs/approval_sla_surfacer/job.go` (new package, mirrors `document_review_surfacer/job.go`'s exact structural shape: `Work` → `authz.WithBackgroundBypass` → `run` → phase 1 single bypass tx `ListTenantsWithOverdueApprovalStages` (new port on `documents/approval`'s published surface) → phase 2 per-tenant seeded tx `ListOverdueApprovalStages` (count/log) + emits notification-fanout outbox rows for newly-overdue stages (idempotent — only stages not already flagged in this due cycle). Alert-only, no auto-action, per ADR 0068 (locked constraint, spec.md §4/§11). Registered in `internal/modules/jobs/maintenance/periodic.go` as a 4th dual-defined periodic job, `PeriodicJobOpts{ID: "approval-sla-surfacer", RunOnStart: false}`, hourly interval (matches `document_review_surfacer`'s cadence).
- `internal/modules/documents/approval/domain` gains the published-port interfaces (`ApprovalSLAReader`, `ApprovalSLAWriter` or similarly named, mirroring `documents/domain.ReviewDueReader`/`ReviewSurfaceWriter`) that the new job consumes — no raw SQL in the jobs package, per the same rule `document_review_surfacer`'s own package doc states.

### Visibility gating (P2/P3/P8)

- `internal/modules/documents/approval/infrastructure/approval_repository.go`: new sentinel `ErrInstanceNotVisible = errors.New("approval: instance not visible to this actor")`.
- `internal/modules/documents/approval/application/read_service.go`: new unexported predicate `instanceVisible(ctx, tx, tenantID, actorID string, inst *domain.Instance) (bool, error)` — true iff actor ∈ {`inst.SubmittedBy`} ∪ {any `EligibleActorIDs` across all `inst.Stages`} ∪ {holds `CapApprovalOversee`} ∪ {holds `CapDocumentEdit`, area-scoped to the instance's resolved area}. `LoadInstance` and `LoadActiveInstanceByDocument` both: (1) keep the existing tier-2 `authz.Require(CapDocumentView, "tenant")` OR `CapApprovalOversee` gate as today (a true 403 case when the actor has neither) — Interview #6's "in the building at all" check; (2) additionally call `instanceVisible`; when false, return `ErrInstanceNotVisible` (404), never falling through to render instance detail to an ineligible bare `document.view` holder.
- `internal/modules/documents/approval/http/errors.go`: new case mapping `errors.Is(err, infrastructure.ErrInstanceNotVisible)` → `http.StatusNotFound` (same problem-type family as `ErrNoActiveInstance`, distinct `code` constant `approvalCodeNotFoundInstanceNotVisible` for audit/debug distinguishability server-side, though the wire status/shape is 404 either way).
- `internal/modules/documents/approval/application/read_service_tenant_grade_view_integration_test.go` (F0.3, pre-existing): updated in place — the "tenant-grade viewer, doc carries an area code, Granted" tests are rewritten to seed a viewer WITHOUT eligibility/oversee/edit and assert `ErrInstanceNotVisible` (404), while a NEW test seeds a viewer who IS in `EligibleActorIDs` (or holds `CapApprovalOversee`/`CapDocumentEdit`) and asserts `Granted`. The no-grant-denied and system_admin-bypass tests are unchanged (still correct under the new rule — system_admin bypasses everything, no-grant is still `ErrCapDenied`).

### Worklist (`/approval/inbox`)

- `internal/modules/documents/approval/application/read_service.go`: `listInboxItems`'s SQL gains two optional filters — `stage_kind` (`AND ($N = '' OR asi.stage_kind = $N)`) and `due_before` (`AND ($N::timestamptz IS NULL OR asi.due_at <= $N::timestamptz)`) — both additive to the existing (already query-layer-scoped) `eligible_actor_ids @> $2::jsonb` predicate; a new `scope` parameter, when `"oversee"` AND the caller holds `CapApprovalOversee` (checked via `authz.Require` inside the same tx, before the query runs), replaces the `eligible_actor_ids @>` predicate with a no-op (tenant-wide, still `tenant_id = $1`-scoped) rather than removing tenant scoping.
- `internal/modules/documents/approval/http/inbox_handler.go`: parses `stage_kind`, `due_before` (RFC3339), `scope` query params; on `scope=oversee` without the capability, the tier-2 `authz.Require` call inside `ListInboxItemsWithTotal`'s oversee branch returns `authz.ErrCapDenied` → existing 403 mapping (unchanged).
- `internal/modules/documents/approval/http/contracts/instance_read.go`: `InboxItem` gains `StageKind string` and `DueAt *string` fields; `InstanceResponse`/`StageInstance` (same file) gain `stage_kind`/`due_at` on `StageInstance` and `frozen_content_hash` (`*string`) on `InstanceResponse` (already computed by F5/F6, simply not yet exposed on the read DTO) — closes the plan.md contract line "Instance DTO exposes `stage_kind`, `due_at`, `frozen_content_hash`".
- `internal/modules/documents/approval/http/get_instance_handler.go`: `mapInstanceResponse` populates the three new fields from `domain.StageInstance.Kind`/`.DueAt` and `domain.Instance.FrozenContentHash`.
- `api/openapi/v1/openapi.yaml`: the approval-tag schemas nearest to `InboxItem`/instance-read gain the mirrored properties (`stage_kind`, `due_at`, `frozen_content_hash`) and the inbox GET route gains the three new optional query params, documented with enum/format; regen via the module's `go generate`/oapi-codegen target (same "hand-maintained live DTO vs generated schema" split F7 already documented — F8 keeps both in sync but the LIVE contract is still `contracts.*`, per F7's established precedent, Non-goals below).

## Non-goals

- **Auto-escalation/auto-cancellation on SLA breach.** Alert-only, per ADR 0068 (locked constraint, spec.md §4/§11) — `approval_sla_surfacer` only surfaces (notification fanout), never mutates instance/stage state.
- **A dedicated "approval history" list endpoint for post-publication visibility (spec §6.3's last bullet).** No such endpoint exists today; the bounded defer in Interview #8 documents this as a real, spec-adjacent ambiguity, not silently resolved.
- **Reconciling the openapi-generated vs hand-maintained DTO split** for the approval-instance read endpoints — pre-existing (F7 Non-goals), untouched here; F8 updates both surfaces in parallel (openapi schema for contract-surface completeness, `contracts.*` for the actually-live wire shape) rather than migrating the handler onto the generated type.
- **Changing `LoadActiveInstanceByDocumentForMutation`'s** (no-visibility-check) contract — mutation services already gate themselves; this method is explicitly out of scope (Interview #7).
- **Re-deriving `due_in_days` from a possibly-newer route version at stage-activation time.** The snapshot (`due_in_days_snapshot`, captured at submit) is authoritative for the life of the instance, exactly like every other `*Snapshot` field on `StageInstance` — consistent with F2's route-version-pinning design (in-flight instances stay pinned to the version they started on).
- **Any change to F1–F7's hash chain, freeze boundary, SoD, or signature-meaning work**, or to F9's delegation (not yet implemented) — F8 is scoped exactly to W4 (SLA) + P2/P3/P8 (visibility) + the worklist filters, per plan.md's feature boundary.
