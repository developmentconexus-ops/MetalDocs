# Feature F9 — `delegation` — spec.md

> **Milestone:** 2b — Approval Kernel Backend  ·  **Feature:** `f9-delegation`
> **Status:** Approved for implementation

## Interview record (self-directed, no operator ambiguity requiring a stop)

| # | Question | Answer |
|---|----------|--------|
| 1 | What is the single, real enforcement choke point delegation must widen, and why must it NOT be a second parallel check? | Both `DecisionService.RecordSignoff` (decision_service.go:282) and `ReviewVerdictService.RecordVerdict` (review_verdict_service.go:132) call the exact same pure predicate, `domain.CheckEligibility(actorUserID, activeStage.EligibleActorIDs)`, immediately followed by the exact same `domain.CheckSoD(instance.SubmittedBy, actorUserID, priorSignoffs)` call. These two predicates ARE the capability-adjacent authz gate for "may this specific actor act on this specific stage" (the tier-2 capability check, `authz.Require(CapDocumentSignoff/CapApprovalReview, area)`, already ran earlier and only proves "this actor holds the capability class somewhere" — eligibility is the per-instance narrowing). Per ADR 0022 (never a second, possibly-divergent rule), F9 must make delegation a widened INPUT to `CheckEligibility` (the actor is eligible if literally in the pool OR if an active delegation makes them act on behalf of someone who is in the pool) — never a separate `if delegated { skip the check }` branch bolted on beside it. |
| 2 | Given `CheckEligibility` is a pure function (no DB access) and delegation rows live in Postgres, where does the DB read happen without creating a second authz path? | The application service (both `RecordSignoff` and `RecordVerdict`) already loads `activeStage.EligibleActorIDs` from the already-loaded `instance` aggregate (frozen at submit). F9 adds one new repository read, `LoadActiveDelegationsFor(ctx, tx, tenantID, actorID, now) ([]Delegation, error)`, called in-tx (same tx as everything else — no off-tx read of authorization-relevant state, unlike the H-PRE-1 display-name reads) immediately before the `CheckEligibility` call. The service computes an "effective actor identity for this action": if `actorID` is directly in `EligibleActorIDs`, act as self (no delegation involved, common case, zero extra query cost avoided is NOT worth it — the query always runs so the "isn't currently delegating" case is provable, not assumed). If not directly eligible, the service checks whether the actor holds an active delegation FROM someone (`delegatorID`) who IS in `EligibleActorIDs`; if so, the pool membership check passes with `onBehalfOf = delegatorID` recorded. `CheckEligibility` itself is called with `EligibleActorIDs` unchanged — the widening happens by trying membership for `actorID` directly, and only on failure, trying each active delegation's `delegatorID` against the same unchanged `EligibleActorIDs` slice via the SAME function, not a different rule. |
| 3 | Does a delegate need a real capability grant (`document.signoff`/`approval.review`) of their own, or does delegation bypass tier-2 capability checks entirely? | The delegate needs their OWN real capability grant. Design spec.md §4 states plainly: "Delegate acts *as themselves on behalf of* — signoff records both identities. No credential sharing, no role impersonation." The tier-2 `authz.Require(CapDocumentSignoff, areaCode)` / `authz.Require(CapApprovalReview, areaCode)` calls (already present, unchanged by F9) still run first and still gate on the delegate's OWN capability grant in that area — delegation never grants a capability the delegate doesn't already hold. What delegation grants is ELIGIBILITY for a SPECIFIC stage instance's frozen pool — i.e., delegation answers "is this specific instance's stage in this actor's worklist", not "does this actor generally have signoff rights." This is consistent with spec.md's explicit non-goal framing (no role impersonation) and keeps the two-tier PDP intact: tier-1/tier-2 capability, unchanged; eligibility (a narrower, per-instance predicate that tier-2 doesn't reach) is where delegation lives. |
| 4 | SoD inheritance ("author's delegate cannot approve author's doc") — how, without breaking the existing `domain.CheckSoD(authorUserID, actorUserID, priorSignoffs)` 2-call-site contract? | `domain.CheckSoD`'s existing rule only ever compared the ACTING actor to the author — it has no notion of "acting on behalf of." Delegation introduces a genuinely new identity in the rule ("the delegator" — the person whose eligibility slot is being filled). The correct predicate, per spec.md §4 ("delegate inherits delegator's SoD constraints"), is: reject if EITHER the acting actor IS the author OR (when acting via delegation) the DELEGATOR is the author. `CheckSoD`'s signature is widened to `CheckSoD(authorUserID, actorUserID string, onBehalfOfUserID string, priorSignoffs []Signoff) error` — a 4th parameter, empty string when acting as self (the overwhelmingly common case, and the two existing call sites already sit inside this same feature's file-list scope per plan.md's own "Modify: SoD — delegate inherits delegator's SoD constraints" line, so this is not an out-of-boundary drive-by. `onBehalfOfUserID == authorUserID` is checked as an ADDITIONAL condition to the existing `actorUserID == authorUserID` check — same single predicate function, same single call site per service, no second SoD rule anywhere. |
| 5 | Does a delegate's action on the cross-stage-reuse clause (`priorSignoffs` cross-stage-already-signed check) apply to the delegator's identity too, or only the delegate's own? | Only the delegate's own `actorUserID` — this clause exists to prevent one physical person from voting twice across stages of the same instance (ballot-stuffing prevention), which is about the ACTING person, not whose "seat" they filled. Design spec.md does not ask for cross-stage delegation-aware exclusion, and inventing one would be scope creep beyond "delegate inherits delegator's SoD constraints" (which is specifically about the author-self-approval rule, not the already-voted rule). Unchanged: `priorSignoffs` is still loaded/checked keyed on `actorUserID` exactly as today. |
| 6 | Is delegation capability-based or instance-based (per the harness's opening question)? | Neither in the "capability reassignment" sense the question implies — and this distinction matters for ADR 0022 compliance. Delegation is NEITHER a new capability grant NOR a role reassignment. It is a time-windowed, tenant-scoped DATA record (`approval_delegations`: delegator_id, delegate_id, starts_at, ends_at, reason) that WIDENS one specific input (the eligible-actor membership test) to one specific application-service call site, while every capability check in the system (tier-1 route→cap, tier-2 `authz.Require`) is completely unaffected and unaware delegation exists. The delegate must independently hold the real capability (`document.signoff`/`approval.review`) in the relevant area — delegation supplies "which stage instance is in your worklist," never "what class of action you may take." This is the correct global-maximum shape per CLAUDE.md's own framing (capabilities never roles) — an instance-scoped ELIGIBILITY grant riding on top of an unchanged capability layer, not a third authz mechanism. |
| 7 | Self-delegation and overlapping windows — what's enforced where? | Self-delegation (`delegator_id == delegate_id`) is rejected at BOTH layers per the standing "app-checks-first, DB-tripwire-last" invariant pattern used throughout M2b: the application service (`DelegationService.CreateDelegation`) returns a typed `ErrSelfDelegation` before any INSERT is attempted, AND the migration's `approval_delegations_no_self` CHECK constraint (plan.md's own migration text) is the DB-level backstop. Overlapping windows for the SAME delegator (e.g. delegating the same period twice, or two different delegates for overlapping windows) are explicitly ALLOWED — spec.md §4: "Overlapping windows for the same delegator are allowed (union semantics — any active delegation makes the delegate eligible)." No uniqueness constraint on (delegator_id, window) is added; `LoadActiveDelegationsFor` returns the full active set and any one active row is sufficient (a union, computed as "does at least one active delegation exist", not "exactly one must exist"). |
| 8 | Revocation — is it a real-time in-tx check, or a soft flag a stale read could miss? | Real-time, in-tx. There is no separate "revoke" mutation that flips a boolean read by a cache — `LoadActiveDelegationsFor`'s WHERE clause is `starts_at <= now() AND ends_at > now()` (server `now()`, not app-clock), evaluated fresh on every `RecordSignoff`/`RecordVerdict` call inside the SAME transaction that performs the state-changing write. "Revocation" in this design IS "the window ends" (or, per the DELETE endpoint below, the row is deleted outright) — there is no `revoked_at` soft-delete column read by one path and ignored by another: a DELETE removes the row so the very next `LoadActiveDelegationsFor` query (which runs at actual use-time, in-tx, not from any cache) cannot see it. This closes the "soft flag ignored by the read path" failure class named in the task brief — there is exactly one read path (the in-tx query at use-time), and it is the only thing that decides eligibility-via-delegation. |
| 9 | Grant/revoke/use audit trail — what events, matching the F1–F8 `GovernanceEvent`/`EventEmitter` pattern? | Three new `EventType` consts, mirroring the existing naming convention (`route.config.created/updated/deactivated`): `EventTypeDelegationGranted = "delegation.granted"`, `EventTypeDelegationRevoked = "delegation.revoked"`. "Use" is NOT a separate governance event — the existing `EventTypeSignoffRecorded`/`EventTypeReviewVerdictRecorded` events already carry the full audit trail for an action; F9 widens their JSON payload with an additive `on_behalf_of` field (present, non-empty, only when the eligibility pass came from a delegation) so "this action was performed via delegation" is visible on the SAME event a plain signoff already produces, rather than a duplicate/parallel "delegation used" event that could drift out of sync with the real signoff/verdict event. This mirrors F7's "signature_meaning added to the existing signoff record, not a new event type" precedent. |
| 10 | Does the delegate's identity get persisted on the signoff/verdict row itself (dual-identity, spec.md §4), and is this a new column on existing tables or a new column on the new table? | New, additive, nullable column on BOTH existing tables: `approval_signoffs.on_behalf_of_user_id text NULL` and `approval_review_verdicts.on_behalf_of_user_id text NULL` (tokens-actor-id-text-contract: TEXT, matching every other actor-id column in this schema family). NULL when the actor acted as themselves (the overwhelming common case, unchanged wire/audit shape); non-NULL = the delegator's user_id when eligibility was satisfied via an active delegation. This is the "dual-identity" persistence spec.md asks for: `actor_user_id` (who physically acted, always populated, unchanged) + `on_behalf_of_user_id` (whose eligibility slot they filled, additive). Not stored on `approval_delegations` itself — that table is the grant/window record, not a per-use log; "which specific signoffs/verdicts used which delegation" is reconstructible from `(actor_user_id, on_behalf_of_user_id, signed_at/verdict_at)` joined against the delegation's window, without a separate join table, avoiding an unrequested M:N usage-log table plan.md's file list does not mention. |
| 11 | What are the delegation HTTP endpoints' exact shape, and do they need contract-first OpenAPI changes? | Yes, contract-first (CLAUDE.md invariant). Two new routes under the existing `approval` tag, mirroring the existing route-admin CRUD's shape (`POST`/`DELETE`, JSON body, `ApprovalDelegation` schema with `id`, `delegator_id`, `delegate_id`, `starts_at`, `ends_at`, `reason`, `created_by`, `created_at`): `POST /api/v1/approval/delegations` (create — body `{delegate_id, starts_at, ends_at, reason}`; `delegator_id` is ALWAYS the calling actor's own id, server-derived from the auth context, never client-supplied — a user delegates THEIR OWN eligibility, they cannot name an arbitrary third party as delegator, which would be a privilege-escalation hole) returns `201` with the full `ApprovalDelegation`; `DELETE /api/v1/approval/delegations/{id}` (revoke — hard-deletes the row; only the delegator OR a `CapApprovalOversee` holder may revoke, enforced via `authz.Require`-adjacent ownership check in-service, since "delegator can revoke their own grant" is an ownership rule, not a capability-class rule, so it does not need a new capability). Both routes gate at tier-1 on `CapDocumentSignoff` (any actor who could plausibly need to delegate their own signoff/review duty already holds `document.signoff` or `approval.review` somewhere — delegation-management itself needs no NEW capability per spec.md's non-goal framing: it never appears in spec.md §6.1's new-capabilities table, which lists only `approval.review`/`approval.oversee`). Tier-2 inside the service re-derives the same rule (delegator-is-self OR oversee) rather than trusting the tier-1 gate alone. |
| 12 | Which migration number, and which table/column names, verified against real current schema (not guessed)? | `db/migrations/0293_approval_delegations.sql` — 0291/0289 were never actually used by any landed migration (F4 ultimately shipped as 0288, F7's SoD trigger as 0290, F8's SLA columns as 0292; grepped `db/migrations/` directory listing directly, confirms 0293 is the next free number, not a guess from plan.md's stale "0291" reference). Table/columns verified against `db/baseline/0001_current_schema.sql:2030-2044` (`approval_signoffs` real column list: no `on_behalf_of_user_id` yet, confirming this is a genuinely new column) and `db/migrations/0288_review_verdicts_changes_requested.sql:36-51` (`approval_review_verdicts` real column list, same conclusion). `approval_delegations` itself: brand new table, plan.md's proposed shape (tenant_id, delegator_id, delegate_id, starts_at, ends_at, reason, created_by, created_at, window CHECK, no-self CHECK) is adopted verbatim — verified no existing table of this name via `Grep "CREATE TABLE.*approval_delegations"` (zero hits). RLS policy shape copied verbatim from `0288`'s `approval_review_verdicts` tenant_isolation policy (same NULL-GUC-permissive idiom, ADR 0027) — but keyed on `tenant_id` directly (not `actor_tenant_id`, since this table has no natural "acting tenant" ambiguity the signoff/verdict tables have; delegator and delegate are always same-tenant by the FK-adjacent invariant that `iam_users` rows are tenant-scoped). |

## Consumer contract

### Schema — `db/migrations/0293_approval_delegations.sql`

```sql
CREATE TABLE public.approval_delegations (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL,
  delegator_id text NOT NULL,
  delegate_id text NOT NULL,
  starts_at timestamptz NOT NULL,
  ends_at timestamptz NOT NULL,
  reason text NOT NULL,
  created_by text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT approval_delegations_window_chk CHECK (ends_at > starts_at),
  CONSTRAINT approval_delegations_no_self CHECK (delegator_id <> delegate_id)
);
ALTER TABLE public.approval_delegations ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.approval_delegations FORCE ROW LEVEL SECURITY;
-- tenant_isolation policy: NULL-GUC-permissive idiom (ADR 0027), keyed on tenant_id.

ALTER TABLE public.approval_signoffs
  ADD COLUMN IF NOT EXISTS on_behalf_of_user_id text;
ALTER TABLE public.approval_review_verdicts
  ADD COLUMN IF NOT EXISTS on_behalf_of_user_id text;
```

Indexes: `(tenant_id, delegate_id, starts_at, ends_at)` to support `LoadActiveDelegationsFor`'s lookup pattern.

### Domain

- `internal/modules/documents/approval/domain/delegation.go` (new): `Delegation` value object (id, tenantID, delegatorID, delegateID, startsAt, endsAt, reason, createdBy, createdAt) + `NewDelegation(params) (*Delegation, error)` validating window (`endsAt > startsAt`) and no-self (`delegatorID != delegateID`) as the app-checks-first line (DB CHECK is the tripwire-last line). `ErrSelfDelegation`, `ErrInvalidDelegationWindow` sentinels.
- `internal/modules/documents/approval/domain/eligibility.go`: unchanged function signature for `CheckEligibility` — no new parameter here; the widening happens at the CALLER (application layer), which tries `CheckEligibility(actorID, pool)` first and, on `ErrActorNotEligible`, tries `CheckEligibility(delegatorID, pool)` for each active delegation's delegator, per Interview #2. A new tiny helper `ResolveEligibleIdentity(actorID string, eligibleActorIDs []string, delegations []Delegation) (onBehalfOf string, err error)` centralizes this two-step logic as ONE pure function (single predicate, testable without DB) so `RecordSignoff` and `RecordVerdict` both call the exact same widened check, not two hand-rolled copies.
- `internal/modules/documents/approval/domain/sod.go`: `CheckSoD`'s signature gains a 4th parameter: `CheckSoD(authorUserID, actorUserID, onBehalfOfUserID string, priorSignoffs []Signoff) error`. Rule: reject if `actorUserID == authorUserID` (unchanged) OR (`onBehalfOfUserID != "" && onBehalfOfUserID == authorUserID`) (new — delegate inherits delegator's SoD constraint). Both existing call sites (decision_service.go:301, review_verdict_service.go:153) updated to pass the resolved `onBehalfOf` value (empty string when acting as self).
- `internal/modules/documents/approval/domain/signoff.go`: `Signoff` gains unexported `onBehalfOfUserID string` + getter `OnBehalfOf() string`; `SignoffParams` gains `OnBehalfOfUserID string` (optional, empty = acting as self); `MarshalJSON` adds `"on_behalf_of_user_id"` (empty string, not omitted, when acting as self — consistent wire shape, no omitempty drift).
- `internal/modules/documents/approval/domain/review_verdict.go`: `ReviewVerdict` gains the identical `onBehalfOfUserID`/`OnBehalfOf()`/`OnBehalfOfUserID` triad, mirroring `Signoff`.

### Repository (`infrastructure/approval_repository.go` interface + `postgres_approval_repository.go` impl)

- `InsertDelegation(ctx, tx, d domain.Delegation) error` — plain INSERT (no idempotency-replay concept needed; a duplicate grant is just two rows, both valid, union semantics per Interview #7).
- `DeleteDelegation(ctx, tx, tenantID, delegationID, callerID string) (deleted bool, delegatorID string, err error)` — deletes the row IFF `tenant_id` matches AND (`delegator_id = callerID` OR caller holds `CapApprovalOversee`, checked by the SERVICE before calling this, not by the repository — repository stays authz-agnostic per existing convention). Returns `delegatorID` for the governance event even after delete (captured before the DELETE via `RETURNING`).
- `LoadActiveDelegationsFor(ctx, tx, tenantID, delegateID string, asOf time.Time) ([]domain.Delegation, error)` — `SELECT ... WHERE tenant_id=$1 AND delegate_id=$2 AND starts_at <= $3 AND ends_at > $3`. Called with `asOf = the DB's own now()` is NOT possible for a Go-side parameter — the service passes `time.Now().UTC()` as `asOf`, matching the existing `Clock` abstraction already used throughout the package (`s.clock.Now()`), so the query is deterministic and testable; this is consistent with how e.g. `PinFrozenHash`/`UpdateStageStatus` use DB-side `now()` for STATE WRITES but reads elsewhere already use the injected `Clock` for comparisons (e.g. nothing in this package currently reads-and-compares against DB `now()` for a SELECT predicate — using the app clock here, passed as a bound parameter, is the same idiom as `submit_service.go`'s `s.clock.Now()` calls, not a new pattern).
- `signature: InsertSignoff`/`InsertVerdict` unchanged (already take the whole `domain.Signoff`/`domain.ReviewVerdict` value; `on_behalf_of_user_id` is added to the fixed column list of both INSERTs, sourced from the new getter).
- `LoadInstance`/`LoadInstancesByIDs`/`LoadPriorSignoffs`/`LoadStageSignoffs`/`LoadStageVerdicts`: SELECT lists gain `on_behalf_of_user_id` so it round-trips into the domain objects (needed for the audit/manifest read path).

### Application (`application/delegation_service.go`, new)

```go
type DelegationService struct {
    repo    infrastructure.ApprovalRepository
    emitter EventEmitter
    clock   Clock
}

type CreateDelegationInput struct {
    TenantID, DelegatorID, DelegateID, Reason string
    StartsAt, EndsAt                          time.Time
}

func (s *DelegationService) CreateDelegation(ctx, runner, in CreateDelegationInput) (domain.Delegation, error)
func (s *DelegationService) RevokeDelegation(ctx, runner, tenantID, delegationID, callerID string, callerIsOversee bool) error
```

- `CreateDelegation`: app-check `domain.NewDelegation` (self/window validation) BEFORE the tx; in-tx INSERT; emits `EventTypeDelegationGranted` governance event (payload: delegator_id, delegate_id, starts_at, ends_at, reason).
- `RevokeDelegation`: in-tx, loads the row (or has `DeleteDelegation` do the ownership-scoped delete atomically via its WHERE clause — chosen: the WHERE-clause approach, since it is a single round-trip and matches the OCC-via-WHERE idiom used throughout this package, e.g. `CancelInstance`'s revision-version WHERE guard); `rows==0` → `ErrDelegationNotFoundOrNotOwned` (a single ambiguous error deliberately — "not found" and "not yours" both 404, mirroring the `ErrInstanceNotVisible` cross-boundary-is-not-found precedent from F8, since exposing "it exists but isn't yours" leaks information about another actor's delegation). Emits `EventTypeDelegationRevoked` on success.
- **`decision_service.go` / `review_verdict_service.go` (the ONLY two files where the actual composition happens):** immediately before the existing `domain.CheckEligibility(req.ActorUserID, activeStage.EligibleActorIDs)` call, both services now:
  1. Try `domain.CheckEligibility(req.ActorUserID, activeStage.EligibleActorIDs)` directly (unchanged fast path — zero added DB read cost is NOT the goal here; the delegation query always runs, see below, so this is purely which code path is tried first, not a cost optimization).
  2. On success, `onBehalfOf := ""`.
  3. On `ErrActorNotEligible`, load `s.repo.LoadActiveDelegationsFor(ctx, tx, req.TenantID, req.ActorUserID, s.clock.Now())` (in-tx, real-time) and try `domain.CheckEligibility(delegation.DelegatorID, activeStage.EligibleActorIDs)` for each returned delegation (SAME function, SAME pool, different candidate identity) — first delegation whose delegator is in the pool wins; `onBehalfOf = that delegation's DelegatorID`.
  4. If neither the direct check nor any delegation resolves, propagate the original `ErrActorNotEligible` (unchanged error/event/audit shape for the true-ineligible case).
  5. `domain.CheckSoD(instance.SubmittedBy, req.ActorUserID, onBehalfOf, priorSignoffs)` (widened call, Interview #4).
  6. `SignoffParams`/`VerdictParams` gain `OnBehalfOfUserID: onBehalfOf`.
  7. The persisted governance event's JSON payload gains `"on_behalf_of": onBehalfOf` (present, possibly empty string) alongside the existing keys.

  This is the ENTIRE production-code composition — no new authz call, no new capability, no branch that could diverge from `CheckEligibility`/`CheckSoD`'s existing single-predicate contracts; delegation only ever supplies a WIDER SET OF CANDIDATE IDENTITIES tried through the exact same two functions every non-delegated call already goes through.

### HTTP (`http/delegation_handler.go`, new; `contracts/delegation.go`, new)

- `api/openapi/v1/openapi.yaml`: new `ApprovalDelegation` schema + `POST /approval/delegations` + `DELETE /approval/delegations/{id}`, tagged `approval`. Regenerated via `go generate ./internal/modules/documents/approval/api/...`.

## Non-goals

- **A capability grant for "manage delegations."** Delegation-of-authority is an ownership action (delegate your OWN eligibility), not a new capability class — spec.md §6.1's new-capabilities table lists only `approval.review`/`approval.oversee`; F9 adds neither `TestCapabilityRegistrySize` bump nor a new tripwire arm.
- **Cross-stage or cross-instance delegation "already voted" exclusion for the delegator's own prior votes.** Interview #5 — out of scope; `priorSignoffs` stays keyed on the acting actor only.
- **A per-use delegation log/join table.** The dual-identity columns on `approval_signoffs`/`approval_review_verdicts` are the audit trail (Interview #10); no new M:N table.
- **Changing any tier-1/tier-2 capability check.** `authz.Require(CapDocumentSignoff | CapApprovalReview, area)` calls in both services are untouched; delegation never substitutes for or bypasses them (Interview #3, #6 — the ADR 0022 constraint this whole feature exists to satisfy).
- **A "who delegated to me" or "my active delegations" listing endpoint.** Not named in plan.md's file list; a future FE-driven need would be its own follow-up.
- **Notification/reminder fanout on delegation grant/expiry.** Not named in plan.md's file list (unlike F8's SLA surfacer); delegation grants are silent except for the governance-event audit trail.
