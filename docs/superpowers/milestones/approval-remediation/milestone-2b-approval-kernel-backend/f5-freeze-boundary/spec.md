## Consumer contract

**Freeze executor** (`application/freeze.go`, new): a function invoked from inside an already-open stage-transition tx (never opens its own tx — mirrors every other approval application function), taking `(ctx, tx, tenantID, instance *domain.Instance, completedStage *domain.StageInstance) error`:

1. **Idempotency guard:** if `instance.FrozenContentHash != nil`, no-op (return nil immediately) — re-entry on an already-frozen instance never re-computes or re-pins.
2. **Comment gate:** `repo.HasUnresolvedInstanceComments(ctx, tx, tenantID, instance.DocumentID, instance.SubmittedAt)` → if true, return `ErrFreezeBlockedByUnresolvedComments` (new sentinel, distinct from `ErrApprovalBlockedByUnresolvedComments` since freeze and final-approve are now different moments per W10).
3. **Markup gate:** NOT invoked in this feature (Interview #2/#3 — no live docx buffer source wired yet). The gate function (`application/markup_gate.go`) is implemented, unit-tested standalone, and exported for the future call site, but `freeze.go` does not call it. This is documented as the feature's single largest bounded defer, not silently omitted.
4. **Hash pin:** `repo.PinFrozenHash(ctx, tx, tenantID, instance.ID, instance.ContentHashAtSubmit, expectedRevisionVersion)` — a CAS UPDATE (`WHERE id=$1 AND tenant_id=$2 AND frozen_content_hash IS NULL`) mirroring `UpdateInstanceStatus`'s `WHERE status=$expected` idiom exactly; zero rows affected (lost the race, or already frozen by a concurrent tx) is NOT an error — it means idempotent/already-frozen, so `PinFrozenHash` returns a boolean "did I win the CAS" rather than erroring on 0 rows (freeze is idempotent by design, not merely tolerant of races — spec.md §2.2 "Freeze idempotency: re-entry on an already-frozen instance is a no-op, hash unchanged").
5. Sets `instance.FrozenContentHash = &hash` on the in-memory aggregate so callers (`RecordVerdict`/`RecordSignoff`/`SubmitRevisionForReview`) see the updated state without a second read.

**Call sites** (all three, per spec.md §2.2's two triggers — "last review stage → first approval stage" and "approval-only routes at submit"):

- `review_verdict_service.go`'s `RecordVerdict`, `ready` branch: after `instance.AdvanceStage()` succeeds, if the just-completed stage (`activeStage`, captured before `AdvanceStage` mutates it) was `StageKindReview` AND (the instance has no more active stage (`instance.Active() == nil`) OR the newly-active next stage is `StageKindApproval`) → call `freeze.Execute(...)` before any document-status transition. This covers both "review stage N → approval stage N+1" and "review stage N was the last stage, all-review route, instance goes straight to InstanceApproved".
- `decision_service.go`'s `RecordSignoff`, quorum-approved branch: symmetric hook for routes where stage transitions happen via signoff (covers "review stage N (via RecordVerdict, already froze) → approval stage N+1 (signed via RecordSignoff)" — by the time `RecordSignoff` runs on stage N+1, freeze already fired when stage N completed; this hook exists for defense-in-depth / different route shapes where an EARLIER signoff-driven stage transition could also be review→approval, though in practice route stages after F1-F4 are ordered such that only `RecordVerdict` can complete a review-kind stage — `RecordSignoff`'s stage-kind guard (existing, unchanged) already prevents signoff on a review-kind stage, so this hook is reachable only for the "next stage is approval, prior stage completed via verdict, instance state re-loaded fresh inside RecordSignoff's own tx" case, which cannot happen mid-signoff since signoff only fires on the CURRENTLY active stage — **conclusion: `decision_service.go` needs NO new freeze hook for the between-stage case; it only needs the submit-time-equivalent no-op** (freeze will already be frozen by the time any approval-kind stage is ever active, because activation of an approval-kind stage only ever happens via `AdvanceStage()` called from a review-verdict completing the prior review stage OR via submit for an approval-first route). This simplifies the implementation: **only `review_verdict_service.go` and `submit_service.go` get new freeze call sites; `decision_service.go` is unchanged apart from the W10 comment-gate removal.**
- `submit_service.go`'s `SubmitRevisionForReview`: after stage-instance creation, when `route.Stages[0].Kind == domain.StageKindApproval` (meaning the route has zero review stages — resolving all stage kinds and confirming none is `StageKindReview` is more robust than checking only stage 0 for a hypothetical review-after-approval shape, but per spec.md "review stage ≠ approval stage" ordering, review stages always precede approval stages in a route, so checking stage 0's kind suffices; defensive: check that NO stage in `route.Stages` is `StageKindReview`) → call `freeze.Execute(...)` immediately after `InsertStageInstances`, before the document status transition. Uses `contentHash` (already computed in this function) as the value to pin, and `req.RevisionVersion` semantics mirror the CAS pattern used for the instance status columns (freeze CAS is keyed on `id`+`tenant_id`+`frozen_content_hash IS NULL`, not on `RevisionVersion`, so no extra param threading needed beyond what's already in scope).

**Repository additions** (`postgres_approval_repository.go` + interface in `approval_repository.go`):
- `PinFrozenHash(ctx, tx, tenantID, instanceID, hash string) (won bool, err error)` — `UPDATE approval_instances SET frozen_content_hash=$1 WHERE id=$2 AND tenant_id=$3 AND frozen_content_hash IS NULL`; `RowsAffected() == 1` → `won=true`; `== 0` → `won=false, err=nil` (idempotent no-op OR CAS loss, both are non-error per spec.md "the loser gets a typed 409... /freeze is idempotent").

  Wait — spec.md §2.2 says the CAS *loser* gets a 409, while idempotent re-entry is a silent no-op. These are different outcomes from the same "0 rows affected" signal and must be disambiguated: **disambiguation rule** — freeze always checks `instance.FrozenContentHash != nil` (from the freshly-loaded, FOR-UPDATE-locked `instance` row, loaded moments earlier in the same tx by `LoadInstance`) BEFORE calling `PinFrozenHash` at all (step 1, the idempotency guard above). Because the enclosing stage-transition tx already holds the instance row `FOR UPDATE` (via `LoadInstance`, same locking `RecordVerdict`/`RecordSignoff`/`SubmitRevisionForReview` already do for every other write in this module), **no concurrent freeze can race past this point** — the row lock serializes all concurrent stage-advance attempts on the same instance, so by the time `PinFrozenHash`'s `UPDATE ... WHERE frozen_content_hash IS NULL` runs, the in-memory `instance.FrozenContentHash` check has already deterministically resolved idempotent-no-op vs. first-time-freeze; the CAS `WHERE` clause is defense-in-depth (matches every other mutating repository method's idiom in this module — never trust the in-memory guard alone) rather than the actual race-resolution mechanism. **The "freeze race: two concurrent advance attempts, one wins CAS, other 409" scenario from spec.md/plan.md is therefore actually resolved by the SAME `FOR UPDATE` row lock + OCC (`ExpectedRevisionVersion`) pattern already in place for every stage transition** — a second concurrent `RecordVerdict`/`RecordSignoff` call on the same instance blocks on the row lock until the first commits, then re-reads a stale `ExpectedRevisionVersion` and gets `infrastructure.ErrStaleRevision` (already mapped to 409 problem+json) before it ever reaches the freeze step. This is not a new concurrency primitive — it is the existing OCC/lock discipline this module already has everywhere, applied to freeze as just one more state mutation inside the same locked tx. No new 409 error type is needed for "freeze race" specifically; `ErrStaleRevision` already covers it.

- `HasUnresolvedInstanceComments(ctx, tx, tenantID, documentID string, since time.Time) (bool, error)` — `SELECT COUNT(*) FROM document_comments WHERE tenant_id=$1 AND document_id=$2 AND resolved_at IS NULL AND created_at >= $3`.

**Markup gate** (`application/markup_gate.go`, new, standalone — not wired to a live call site this feature, per Interview #2/#3): `ScanForUnresolvedMarkup(docxBytes []byte) error` — unzips via `archive/zip.NewReader`, reads `word/document.xml`, does a streaming `encoding/xml.Decoder` token scan for start-elements with local name in `{ins, del, pPrChange, commentRangeStart, commentReference}` (namespace-qualified `w:` prefix resolved via the decoder's `Name.Local`, which strips namespace prefixes already — matching on `Local` avoids brittleness to whichever prefix alias the docx XML declares `w:` as). Returns `ErrUnresolvedTrackedChanges` for `ins`/`del`/`pPrChange` matches, `ErrUnstrippedComments` for `commentRangeStart`/`commentReference` matches (distinct sentinels per plan.md's test-case list). No `word/document.xml` entry in the zip, or a corrupt zip → `ErrInvalidDocxBuffer` (new sentinel, fail-closed — never treated as "clean").

## Non-goals

- **Live docx-buffer freeze gating** (calling `ScanForUnresolvedMarkup` from `freeze.Execute` against a real MinIO-fetched buffer) — bounded defer, see Interview #2/#3/#7 and Bounded defers table. The function is built, tested, and ready; the call site and byte-source port are not wired in this feature.
- **F6's no-fallback hash-chain read-path work** (deleting the `COALESCE` in `LoadActiveDocumentContentHash`/`active_instance_reader.go`, making signoff/publish read ONLY the frozen pin) — explicitly F6's scope per the task brief and plan.md. F5 only WRITES `frozen_content_hash`; F5 does not change what `LoadActiveDocumentContentHash` or `active_instance_reader.go` read. Both files are untouched by this feature.
- **Editor-session write-blocking after freeze** (FE `ReviewDocumentCanvas` opening a writable session during `under_review`, or a backend 409 on an edit-save endpoint post-freeze) — M2c/FE scope per spec.md §2.2 point 4 and §8. No backend edit-save endpoint gains a new freeze check in this feature (none currently exists that would need one at the approval layer — document-content writes during `under_review` are today gated by document-status transitions, not by approval-instance freeze state, and adding that specific new guard is out of plan.md's F5 file list).
- **Deleting `HasUnresolvedComments`** (the document-wide, non-instance-scoped method) — kept as dead-but-compiling after the W10 call-site removal; bounded defer (Interview #8).
- **Route-shape validation forcing review-before-approval stage ordering** — F5 assumes (per spec.md's narrative and F1-F4's implementation) that review stages always precede approval stages in a route; no new validation is added to `route.Validate()` to enforce this ordering, since no existing route-admin code (F2) constrains stage-kind ordering either — out of scope, flagged for F2/route-admin territory if it ever becomes a real gap (not observed as a live defect: `route_admin_service.go` was read during F2 and does not order-validate stage kinds today, but no route-admin test exercises approval-before-review either, so this is a latent gap in F2's territory, not introduced or worsened by F5).
