## Interview record (self-directed, no operator ambiguity requiring a stop)

| # | Question | Answer |
|---|----------|--------|
| 1 | What does `LoadActiveDocumentContentHash` actually read today, precisely? | `postgres_approval_repository.go:1422-1444`: `SELECT COALESCE(d.content_hash_at_submit, (SELECT r.content_hash FROM document_revisions r WHERE r.document_id = d.id ORDER BY r.created_at DESC LIMIT 1)) FROM documents d WHERE d.id=$1 AND d.tenant_id=$2`. This reads `documents.content_hash_at_submit` (nullable, baseline `db/baseline/0001_current_schema.sql:1872`) — a **different column on a different table** than `approval_instances.content_hash_at_submit` (NOT NULL, line 1978) or the F5-introduced `approval_instances.frozen_content_hash` (F1/migration 0286, `^[0-9a-f]{64}$` CHECK). The spec's 68a0b3b8 addendum's characterization ("COALESCE fallback to the head revision hash") is confirmed exactly: `documents.content_hash_at_submit` can be legitimately NULL (pre-submit / drafts that never went to `content_hash_at_submit`-writing code) and the COALESCE silently substitutes the latest `document_revisions.content_hash` — which, post-F5, can be a HEAD revision hash captured *after* the instance froze, i.e. floating content the signer never actually reviewed. |
| 2 | Is the "fix" a one-line hash-source swap, or a bigger split? | A split. Two structurally different callers read through the same COALESCE today: (a) `decision_service.go`'s `RecordSignoff` — compares the pinned value against a client-echoed hash at signature time; the ONLY correct source post-freeze is `approval_instances.frozen_content_hash`; there is no legitimate reason for signoff to ever consult a live `document_revisions` row, because by the time any signoff is possible the instance is already frozen (F5: freeze fires at the review→approval boundary or at submit for approval-only routes, strictly before any approval-kind stage — where signoff occurs — ever activates). (b) `active_instance_reader.go`'s `ActiveInstanceForControlledDocument` — a **display** read for the FE's active-document endpoint, which must answer correctly for BOTH a draft (no instance, no freeze yet — legitimately wants the head revision hash) AND a frozen in-flight instance (must echo the SAME value signoff will compare against, per the existing doc comment "mirrors the COALESCE used by the /active-document endpoint so the value compared on signoff matches what the FE received"). These are two different questions ("what does the signer sign against" vs "what hash does the FE currently have loaded") that were incorrectly modeled as one polymorphic COALESCE. Per the locked no-fallback principle (spec §11) and CLAUDE.md/memory ("explicit status-scoped queries over polymorphic fallback"), they must become two explicit branches. |
| 3 | For the display path (`active_instance_reader.go`), what is the correct status-explicit split? | Per F5: freeze fires (i) at submit for approval-only routes (frozen immediately, `under_review` from the first moment), or (ii) at the review→approval stage boundary for routes with review stages. So an active document whose status is in `activeInstanceStatuses` (`draft`, `under_review`, `approved`, `scheduled`) may or may not have a frozen instance yet. The correct rule: if an in-progress `approval_instances` row exists for the document AND its `frozen_content_hash` is non-NULL, that IS the authoritative "current content hash" (frozen, immutable, matches what signoff will compare) — return it. Otherwise (no instance, or instance not yet frozen — e.g. still in a review stage pre-freeze) fall through to the head `document_revisions.content_hash` for that document, which is the only meaningful "current content" answer while nothing is pinned yet. This is NOT a COALESCE over two DB expressions merged into one nullable column read — it is an explicit two-step resolution: (1) try to load the frozen pin for an in-progress instance; (2) if none, load the head revision hash. Both steps are independent, typed queries; neither silently substitutes a value for a state the code cannot actually distinguish. |
| 4 | Does `documents.content_hash_at_submit` (the column, not `approval_instances`') still have any legitimate live reader anywhere, or is the whole column now dead weight for this read-path? | It is dead for the active-instance display query (`active_instance_reader.go`) once replaced by the frozen-pin/head-revision split above — grep confirms `active_instance_reader.go` is its only production reader outside `documents/application/service.go`'s write path (which sets it at submit and is unaffected by F6 — write-path scope is documents/application, not approval, and out of bounds for this feature per plan.md's file list). The column itself is not dropped in F6 (schema deletion is a separate, larger, out-of-scope migration decision — dropping a NOT NULL-adjacent, still-written column requires its own expand/contract review, not bundled into a read-path fail-closed fix); only the read site that COALESCEs over it is deleted. |
| 5 | Does `decision_service.go`'s signoff path need the client-echoed-hash comparison to change shape, or just its source? | Just its source. The existing flow (`clientContentHash(req.ContentFormData)` compared against the repo-loaded value) is architecturally sound — client echoes what it loaded, server verifies no drift. Only the repo-loaded value's origin changes: from the `documents`-table COALESCE to `approval_instances.frozen_content_hash`, read via a renamed method `LoadFrozenContentHash` that does `SELECT frozen_content_hash FROM approval_instances WHERE id=$1 AND tenant_id=$2` scoped by **instance ID** (not document ID — the repository already has `instance.ID` in scope at the signoff call site; using instance ID is strictly more precise than document ID, since a document has at most one in-progress instance at a time but keying on the instance itself removes any ambiguity and matches `PinFrozenHash`'s own `WHERE id=$instanceID` shape). NULL (not yet frozen — should be structurally impossible at signoff time per F5, since only approval-kind stages accept signoff and freeze always precedes their activation) or missing row → `ErrNoActiveContentHash` (existing sentinel, reused — already mapped to `ErrContentHashMismatch` → 412 Precondition Failed at the HTTP boundary, so no new error-mapping wiring is needed). |
| 6 | Does `publish_service.go` need a new hash-chain verification, or is that out of scope? | Reviewed `publish_service.go` in full: `PublishApproved` today verifies instance status (`InstanceApproved`) and OCC revision version, but performs **no content-hash check at all** — it never reads `frozen_content_hash` or any hash. Plan.md's F6 file list says "publish verifies frozen pin (fail closed)". Adding a NEW verification step (publish re-checks `frozen_content_hash` is non-NULL before allowing publish) is in-scope and consistent with "one canonical hash chain: pin at freeze → echo at signoff → verify at publish — no substitute value at any link" (spec §2 point 3). This is an ADDITIVE fail-closed guard (an approved instance that somehow reached `InstanceApproved` without ever freezing — which should be structurally impossible per F5/F4 stage-kind gating, but the whole point of "no-fallback" is to make impossible states loudly detectable rather than silently tolerated) — not a behavior change for any currently-passing path, since every real `InstanceApproved` instance already has a non-NULL `frozen_content_hash` by construction. This is exactly the "P0001 tripwire last line of defense" pattern applied at the read/verify layer instead of a DB trigger, appropriate here because there is no separate mutating write to gate (publish's own UPDATE doesn't touch the hash column) — a fail-closed **read-and-check**, not a new CAS. |
| 7 | Any other production COALESCE-over-hash site in the approval/documents read path not yet named? | Grepped `COALESCE` across `internal/modules/documents/` and `internal/modules/documents/approval/`: exactly two production hits — `postgres_approval_repository.go:1425` (`LoadActiveDocumentContentHash`, addressed) and `active_instance_reader.go:54` (addressed). No third site. (Unrelated COALESCEs elsewhere in the repository, e.g. `loadVerdictByStageActor`'s `coalesce(v.comment,'')`, are display-string null-to-empty-string normalizations, not integrity/hash substitutions — out of scope, correctly untouched, confirmed by the no-fallback principle's own carve-out: "where two states legitimately need different answers, model them as explicit status-scoped queries" applies to identity/integrity reads, not cosmetic string defaults.) |
| 8 | Does the parity test (`active_instance_parity_test.go`) need to change, and how does the "one FULL OUTER JOIN raw SQL vs ported adapter" pattern survive a two-step (not one-query) resolution? | Yes. The test's `rawGetActiveInstance` helper currently replays the OLD single-query COALESCE verbatim as the "ground truth baseline" — that baseline itself contains the defect being fixed, so it can no longer be the comparison target unchanged. Per plan.md: "parity test mirrors new split queries." The helper is updated to replay the NEW two-step resolution (frozen pin for an in-progress instance, else head revision) so the test continues to prove "the adapter does exactly what a hand-rolled raw-SQL reader would do" — now against the corrected logic, not the old defect. This keeps the test's actual purpose (adapter/raw-SQL parity, not a golden defect snapshot) intact. |

## Consumer contract

**Signoff / decision path** (`internal/modules/documents/approval/infrastructure/postgres_approval_repository.go`, `internal/modules/documents/approval/infrastructure/approval_repository.go`, `internal/modules/documents/approval/application/decision_service.go`):

- `LoadActiveDocumentContentHash(ctx, tx, tenantID, documentID) (string, error)` is renamed to `LoadFrozenContentHash(ctx, tx, tenantID, instanceID) (string, error)` — signature changes from `documentID` to `instanceID` (the caller, `decision_service.go`, already has `instance.ID` and `req.InstanceID` in scope; this is a rename + resource-key correction, not new plumbing).
- New body: `SELECT frozen_content_hash FROM approval_instances WHERE id = $1 AND tenant_id = $2` — **no COALESCE, no subquery fallback**. `sql.ErrNoRows` (bad instance id) or a valid row with a NULL `frozen_content_hash` (not yet frozen) both return `ErrNoActiveContentHash` (existing sentinel, reused verbatim — its doc comment is updated to describe the new source).
- `decision_service.go`'s `RecordSignoff` call site updates the call from `s.repo.LoadActiveDocumentContentHash(ctx, tx, req.TenantID, instance.DocumentID)` to `s.repo.LoadFrozenContentHash(ctx, tx, req.TenantID, instance.ID)`. The existing `errors.Is(err, infrastructure.ErrNoActiveContentHash) → return ErrContentHashMismatch` mapping is unchanged (same sentinel, same 412 mapping at the HTTP boundary — `http/errors.go:189-191`).

**Publish path** (`internal/modules/documents/approval/application/publish_service.go`):

- `PublishApproved`, after loading `instance` and confirming `instance.Status == domain.InstanceApproved` (existing check), adds: if `instance.FrozenContentHash == nil`, return `ErrNoActiveContentHash` (reused sentinel — same HTTP mapping path as signoff, since `http/errors.go`'s `ErrContentHashMismatch` case already covers the module-level `application.ErrContentHashMismatch`; publish_service returns the infrastructure-level sentinel directly since it never had its own hash-mismatch error before — confirmed the HTTP error mapper (`errors.go`) already unwraps `errors.Is` against the infrastructure package for other cases, so mapping is extended there, see Non-goals for the one new touch to `http/errors.go`). No re-verification against the client is added (publish has no client-supplied hash to compare against — publish's contract has never required a `_content_hash` echo — this feature does not add one; it only asserts the pin **exists**, per plan.md "publish verifies frozen pin (fail closed)").

**Display path** (`internal/modules/documents/infrastructure/active_instance_reader.go`):

- `ActiveInstanceForControlledDocument` deletes the `COALESCE(active.content_hash_at_submit, (SELECT ... document_revisions ...))` expression from the main projection query — the main query no longer selects `active.content_hash_at_submit` or resolves any hash at all; `contentHash`/`view.ContentHash` are resolved by two follow-up, explicit, status-scoped queries run AFTER the existing `FULL OUTER JOIN` projection resolves `view.DocumentID`/`view.Status`:
  1. If `view.DocumentID != nil` and `view.Status != nil` and `*view.Status == DocStatusUnderReview` (the same condition already guarding the existing in-progress-approval-instance lookup a few lines below): query `SELECT frozen_content_hash FROM approval_instances WHERE document_id=$1 AND tenant_id=$2 AND status=$3 ORDER BY submitted_at DESC LIMIT 1` (status = `InstanceInProgress`, same predicate shape as the existing approval-instance-id lookup) — reuses the SAME row already being fetched for `view.ApprovalInstanceID` (both come from the identical `WHERE` predicate), so this is folded into the SAME existing query as an additional selected column (`frozen_content_hash`) rather than a third round-trip. If the returned `frozen_content_hash` is non-NULL, that is `view.ContentHash`.
  2. Otherwise (no in-progress instance row, OR instance row exists but not yet frozen, OR document status is not `under_review` at all e.g. `draft`/`approved`/`scheduled`/no active doc): fall through to a separate explicit query `SELECT content_hash FROM document_revisions WHERE document_id=$1 ORDER BY created_at DESC LIMIT 1` for the head revision hash.
  - Both branches are plain typed reads; neither is a COALESCE expression. A document with an in-progress-but-not-yet-frozen instance (mid-review, pre-freeze) correctly falls to the head-revision branch — this is the SAME value the old COALESCE would have returned for that state (harmless, since the old code's fallback was only a defect when it silently fired for an ALREADY-frozen instance; for a genuinely-unfrozen in-progress instance, "head revision hash" is the only correct answer today, since nothing is pinned yet to be authoritative).
- `tests/integration/controlleddocuments/active_instance_parity_test.go`'s `rawGetActiveInstance` helper is updated to replay the same new two-step logic (Interview #8) so the parity test continues to validate "the port and a hand-rolled raw-SQL reader agree," now against the corrected logic.

## Non-goals

- **Dropping the `documents.content_hash_at_submit` column** — the column stays; only `active_instance_reader.go`'s read of it via COALESCE is removed. Column-level schema cleanup (confirming zero remaining readers/writers repo-wide, then an expand/contract migration to drop it) is a separate, larger decision out of this feature's file list and out of the no-fallback principle's scope (that principle governs *read semantics*, not schema minimization).
- **Adding a client-echoed hash check to publish** — publish's fail-closed guard only asserts the frozen pin exists; it does not add a new request field or a new client-comparison contract. `api/openapi/v1/openapi.yaml` is untouched by this feature (plan.md's F6 file list has no contract change — confirmed: publish's existing request shape already has everything it needs, `ExpectedRevisionVersion`, and adding hash-echo to publish is not in the locked spec text, which only says "publish verifies frozen pin," i.e. server-side existence, not a client round-trip).
- **Re-deriving `frozen_content_hash` at read time** — F6 never recomputes a hash; it only changes WHICH already-persisted column is read at each of the three call sites (signoff, publish, display). Hash computation itself (`ComputeContentHash`, `PinFrozenHash`) is F1/F5's scope, untouched here.
- **The markup-gate / live-docx-buffer wiring** — F5's bounded defer (no live byte-read path exists yet); F6 is exclusively about which already-persisted column integrity-critical reads consult, never about producing a new hash source. Explicitly called out as orthogonal in the task brief; confirmed unrelated by code inspection (F6 touches zero markup-gate files).
- **Any change to `document_revisions.content_hash` write-path or `documents.content_hash_at_submit` write-path** — both stay exactly as currently written (`documents/application/service.go`); F6 is read-path-only, per plan.md's explicit file list (no `documents/application/service.go` entry).
