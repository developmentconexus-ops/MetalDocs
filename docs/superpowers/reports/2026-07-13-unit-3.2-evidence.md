## Architecture notes (surface to hub, out of unit-3.2 boundary)
- **Fixed role enums are pre-existing, not introduced here.** ActorSelector storage
  (`approval_route_stage_selectors.role` = free text, no value CHECK) and the resolver
  (`WHERE role = $role`, any string) are role-agnostic — a future tenant-defined role
  (e.g. `production_admin`) works with zero migration. The hardcoded role enums are the
  pre-existing CHECKs `user_process_areas_role_check` and `chk_iam_user_roles_role_code`
  on the membership/iam-assignment tables. Those are the local-maximum a future
  role-management feature must retire (tenant-scoped roles table + FK, not a frozen
  ARRAY CHECK). ActorSelector is already forward-compatible. Capabilities invariant
  intact: pool = role_in_area (BPMN candidateGroups grouping), authority = RequiredCapability.

## HS-1 items (for operator gate)
- **Multi-selector drift representation (carried).** B3 says pool selectors
  "re-evaluate per drift policy" and the snapshot columns stay untouched. A
  *single*-selector stage of any kind is fully represented by the resolved
  `AreaCodeSnapshot`/`RequiredRoleSnapshot` (document-area resolves to a concrete
  area at submit; named_user is drift-exempt), so the existing decision/review
  drift path keeps working unchanged — this is the parity guarantee. But a stage
  with **2+ selectors** (a genuine union) cannot be represented by the two single
  snapshot columns, so drift re-eval for multi-selector pools has no representation
  yet. Not reachable in production until multi-selector routes can be authored (FE
  slice 7). RESOLUTION OPTIONS to settle before slice 6/close: (a) drift re-reads
  the pinned route-version's stage selectors (RouteVersionSnapshot already pinned,
  route versions immutable) — keeps snapshot columns untouched; or (b) accept
  single-selector-only drift for v1 and gate multi-selector authoring. Surface to
  hub for a decision; slice 3 stays scoped to submit-time union + parity.
