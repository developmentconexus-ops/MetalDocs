## 1. BLOCKER — dev postgres :5433 wedged in end-of-recovery checkpoint

Unit 4.6's entry gate requires a live DB. `metaldocs-postgres` is not reachable and does not self-heal.

**Symptom:** `pg_isready` → `rejecting connections`; `FATAL: the database system is not yet accepting connections / DETAIL: Consistent recovery state has not been yet reached.`

**Sequence (from container logs + `/proc`):**
| Fact | Evidence |
|---|---|
| Crashed once already *during* a previous recovery | `database system was shut down in recovery at 2026-07-14 16:09:52 UTC` |
| WAL redo **completes** in ~100s | `redo starts at 8/5C782AC0` (17:32:22) → `redo done at 8/70D7BC98 ... elapsed: 101.70 s` (17:34:04) |
| Redo is dominated by clone churn | repeated `WAL redo at ... for Database/DROP: dir 1663/379806` records |

| Zero IO progress | `docker stats` BlockIO `192MB / 508MB` unchanged across a 45s window; container CPU 0.01% |
| **Deterministic, not a one-off** | reproduced across 2 independent restarts (17:32 start → wedge; ~18:25 restart → redo again → same wedge at 14:23 elapsed). A 15-min readiness waiter expired with PG still rejecting. |

**Ruled out:**
- **Disk full** — `/var/lib/postgresql/data` (`/dev/sde`) 1007G total, **933G avail (3% used)**; host C: 246.9GB free.
- **Docker VM IO stack broken generally** — a fresh `docker run --rm alpine df -h /` runs fine.
- **PGDATA size** — 1.3G total, 96 dirs under `base/` (orphan clones from killed runs; small).
- **Windows bind-mount on PGDATA** — PGDATA is a *named volume* (`compose_metaldocs_postgres_data` → `/dev/sde`, VM-side ext4). Only the three `db/*.sql` initdb scripts are bind-mounted.

Deeper kernel forensics (`/proc/27/stack`, `/proc/27/io`, `/proc/27/syscall`) are blocked by container hardening even as root — `Operation not permitted`.

**Assessment:** the wedge is in the Docker Desktop VM's fsync/disk layer for this specific volume, triggered by an end-of-recovery checkpoint over a PGDATA carrying ~96 orphan clone databases. It is a restart→redo→wedge loop and will not clear on its own.

**Shared infra = hub owns it** (HARNESS §2: "the hub owns shared infra; chips never take it"; §9.3a). This unit took no corrective action on :5433 and will not.

**Smallest unblock asks, ranked (hub/operator decision):**
1. **Restart Docker Desktop / the VM** — clears a wedged VM disk layer. Non-destructive. Try first.
2. **If it re-wedges: recreate the postgres volume** — `docker compose down` + `docker volume rm compose_metaldocs_postgres_data` + `up -d postgres`. The compose already mounts `db/prerequisites/0001_extensions.sql`, `db/baseline/0001_current_schema.sql`, `db/reference-data/0001_product_reference_data.sql` as `/docker-entrypoint-initdb.d/*`, so initdb re-bootstraps automatically, and the testdb template rebuilds on first `Open` (content-addressed, `testdb/db.go:143`). Cost = dev row data only (re-seedable); test DBs are disposable by design. **Destructive → needs explicit operator/hub OK.**

**Corroboration for 4.6's own diagnosis:** the WAL being replayed is largely `Database/DROP` records. The per-test `CREATE DATABASE ... TEMPLATE` / `DROP DATABASE` churn that unit 4.6 exists to eliminate is what produced the WAL volume and the 96-directory PGDATA that the checkpoint is choking on. The current test-isolation design is not merely slow — on this platform it is destabilising the dev database.

### 4.4 Design-decisive finding — the hazard is the *handle*, not the *database*

Three independent investigators converged on this. The dominant FRESH-CLONE driver is **not** genuine isolation need — it is per-test mutation of shared `*sql.DB` / DB-level state that is only safe today *because* every test owns a private DB:

- **`ALTER DATABASE "<dbName>" SET search_path TO public, metaldocs`** — 9 files (approval ×2, documents ×4, templates ×3). Every site sets the **same** value; none *tests* search_path. Pure setup boilerplate compensating for the clone's default.
- **`db.SetMaxOpenConns(1)`** — pervasive (~15+ files). Pool-wide; on a shared handle one test clamps every later test in the package.
- **`testdb.SetCapsOnDB(...)`** — session-level `set_config` on a pooled connection; leaks to whatever test next draws that connection.

**Consequence for the design:** if `Open(t)` returns a *shared package handle*, ~20 files stay on the slow clone path for reasons that are artifacts, not requirements. If instead **the factory owns the handle** — `Open(t)` returns a **per-test `*sql.DB` (own pool) onto the package-leased database**, with `search_path` supplied via the **DSN connect parameter** rather than `ALTER DATABASE`, and the pool closed at test end — then all three hazard classes evaporate: `SetMaxOpenConns` becomes test-local, session GUCs die with the pool, and the `ALTER DATABASE` sites can be deleted rather than accommodated.

This is the difference between the decisive lever converting ~130 files or ~110. It requires touching those 9 test files to drop their `ALTER DATABASE` line — **a scope question for the hub**, since the charter's hard rule ("a test that mutates schema or session/DB defaults must keep fresh-clone semantics") would otherwise pin them to clones on a technicality, when the correct fix is to stop the boilerplate mutation at the factory seam. Not absorbed unilaterally.

Verified `metaldocs.tenants`, `role_capabilities`, `schema_migrations` have **zero outbound FKs**; the templates pair references only each other + `tenants`. **Partition B is a closed cluster — no CASCADE can reach it.** A single `TRUNCATE <58 tables> RESTART IDENTITY CASCADE` is the correct shape; no manual ordering needed.

Plus a post-reset row-count invariant (`tenants == 1`, `templates_template == 1`) failing **loud** — no-fallback principle.
- **Verdict: viable, no blockers.**

## 8. Charter premise CORRECTED — lever 5 is not a 2-line delete

Charter: "Delete the 2 redundant `rivermigrate.Migrate` calls (~273s); template already bakes River schema at `db.go:491`."

The premise is right; the prescription is not. Both tests deliberately migrate into a **uniquely-named private schema** (`river_task1_<ts>` at `client_test.go:41`; `river_h_pre_1_<ts>` at `singleton_integration_test.go:68`) — **not** the default schema the template baked. Deleting only the `Migrate()` call while still creating that empty schema breaks the test with `42P01 relation "river_job" does not exist`.

Neither test validates River migration itself — no assertion on migration version, idempotent re-run, or applied-migrations table. `client_test.go` proves `InsertTx` transactional visibility; `singleton_integration_test.go` proves exactly-once dequeue across two clients (the H-PRE-1 retirement proof). So **no coverage is lost by removal.**

Correct change (per test, ~3 lines): drop `CREATE SCHEMA` + `DROP SCHEMA ... CASCADE` cleanup, drop `Migrate()`, and set `riverjobs.Config{Schema: ""}` to use the already-migrated default schema. Safe because both files are FRESH-CLONE (own physical DB), so the private-schema indirection is no longer load-bearing for isolation.
