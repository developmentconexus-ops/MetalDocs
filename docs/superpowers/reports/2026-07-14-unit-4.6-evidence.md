### 3.2 Verdict — the charter's dominant-cost claim is WRONG

The charter states: *"dominant cost = per-test physical CREATE DATABASE clones … amplified by contention"*, and instructs that this not be re-derived. The entry gate exists precisely to test that split, and it comes out the other way:

| Term | Measured | Charter's premise |
|---|---|---|
| Physical clone (`CREATE DATABASE ... TEMPLATE`) | **0.14–0.51s** warm | "dominant cost" |
| Steady-state DROP | 0.37–0.83s | not called out |
| Template build | 62.5s **once per fingerprint** | acknowledged, amortized |
| tenantdata solo, warm | **~11–27s** | 14.6s ✓ |
| tenantdata in full run | **356s** | 356s ✓ |

Clone + drop together cost **~1s per test solo** against an 11 MB template. Four clones = ~3.3s of tenantdata's ~11s. That cannot produce 356s. The **~24× gap between solo and full-run is contention, and contention is essentially the entire cost.**

**This does not reorder the levers — it re-grounds them.** Levers 1/3/4 remain correct and top-ranked, but the reason changes, and the reason determines the design:

- We are **not** removing clones because a clone is expensive (it is ~0.3s). We are removing them because **`CREATE`/`DROP DATABASE` serialize catastrophically under concurrency** — they take cluster-wide locks and `DROP DATABASE` forces a checkpoint. The pathology is the *concurrent* behaviour, not the unit cost.
- Consequence for **lever 2**: adding `-p=4 -parallel=8` *before* lever 1 would multiply the contending operation, not divide the wall time. The charter's "ONLY after lever 1" ordering is confirmed by measurement, not just prudence.
- Consequence for **lever 7** (explicit `STRATEGY = WAL_LOG` as a regression guard): now clearly right for the stated reason (0 saving, cheap guard). An 11 MB template is far below any threshold where `FILE_COPY` would pay.

### 3.2a Contention curve — **lever 2's `-p=4` is a REGRESSION, measured**

The charter prescribes "explicit `-p=4 -parallel=8` in `scripts/test-integration.ps1`". Before implementing that, I measured it. Same 6 clone-using packages (`tenantdata`, `migrations`, `security`, `documents`, `audit`, `templates`), warm template, `-count=1`, only `-p` varying. Artifacts: `.artifacts/contention-p{16,4,1}.log`.

| `-p` | Wall | vs best |
|---|---|---|
| **16** (= NumCPU, today's implicit default) | **125.0s** | — |
| 4 (charter's prescription) | 181.5s | **+45%** |
| 1 | 215.7s | +73% |

Per-package, same runs:

| Package | `-p=1` | `-p=4` | `-p=16` |
|---|---|---|---|
| tenantdata | 12.0s | 40.8s | 52.0s |
| migrations | 96.3s | 171.7s | 115.3s |
| security | 13.9s | 44.0s | 53.1s |
| documents | 34.3s | 73.3s | 60.5s |
| audit | 16.4s | 41.3s | 52.9s |
| templates | 10.7s | 29.2s | 46.8s |

**Two facts, and they point the same way:**

1. **Contention is real and large** — tenantdata inflates 12.0s → 52.0s (4.3×) purely from concurrent packages. This confirms §3.2's diagnosis.
2. **But throttling concurrency makes the wall clock WORSE, not better.** Overlap repays the per-package inflation several times over. `-p=1` pays no contention at all and is the *slowest* configuration by 73%.

**So the charter's `-p=4` must not be implemented as written — it would regress the suite ~45%.** The runner passing no `-p` today is not an oversight to correct; `go test` already defaults `-p` to NumCPU (16 here), which is near-optimal for wall clock.

**Where the win actually is.** At high `-p`, wall ≈ **the slowest package** (migrations 115.3s ≈ the 125.0s wall). Cross-package parallelism is already saturated, so the only remaining lever is **making individual packages faster** — i.e. removing per-test clone+drop (lever 1) and then adding *within*-package parallelism via `t.Parallel` + `-parallel`, which lever 1 is the precondition for. The charter's "lever 2 ONLY after lever 1" ordering survives; its `-p=4` half does not.

**Revised lever 2 spec (proposed, hub to ratify):** keep `-p` at the default (do not pin it to 4); add `t.Parallel()` to reset-safe tests and set `-parallel` explicitly, after lever 1 lands. Re-measure the `-p` curve after lever 1, since removing the clone/drop contention changes the optimum.

**Caveat on this data — stated, not buried:** one sample per configuration. The wall-clock ordering is monotonic and the p=16-vs-p=1 gap (125.0 vs 215.7) is far outside plausible noise, so the conclusion "do not throttle to `-p=4`" is safe. But per-package numbers are noisy (migrations reads 96.3 / 171.7 / 115.3 — non-monotonic), so no per-package claim should be drawn from this table beyond the tenantdata inflation, which the §3.1 solo baseline independently corroborates.

### 3.3 The first DROP took 42s — and it is the wedge mechanism

`drop_database` = **42.38s** on test 1, then 0.37–1.36s on every subsequent test. That is not size (every clone is the same 11 MB). `DROP DATABASE` **forces a checkpoint**; the first drop after a 62.5s template build has to flush that build's entire dirty-buffer backlog.

This is the direct mechanistic link to §1: the operation that wedged the cluster in uninterruptible D-state *is the checkpoint that per-test `DROP DATABASE` forces*. The suite does not merely leave orphan databases behind — **it forces a checkpoint per test**, and on this platform's disk layer that is the operation that hangs. Lever 4 (stop per-test DROP; drop at lease end) is therefore not a minor optimization; it removes the outage mechanism. Recorded per hub's request that §1 be folded in as motivation.

### 4.4 Design-decisive finding — the hazard is the *handle*, not the *database*

Three independent investigators converged on this. The dominant FRESH-CLONE driver is **not** genuine isolation need — it is per-test mutation of shared `*sql.DB` / DB-level state that is only safe today *because* every test owns a private DB:

- **`ALTER DATABASE "<dbName>" SET search_path TO public, metaldocs`** — 9 files (approval ×2, documents ×4, templates ×3). Every site sets the **same** value; none *tests* search_path. Pure setup boilerplate compensating for the clone's default.
- **`db.SetMaxOpenConns(1)`** — pervasive (~15+ files). Pool-wide; on a shared handle one test clamps every later test in the package.
- **`testdb.SetCapsOnDB(...)`** — session-level `set_config` on a pooled connection; leaks to whatever test next draws that connection.

**Consequence for the design:** if `Open(t)` returns a *shared package handle*, ~20 files stay on the slow clone path for reasons that are artifacts, not requirements. If instead **the factory owns the handle** — `Open(t)` returns a **per-test `*sql.DB` (own pool) onto the package-leased database**, with `search_path` supplied via the **DSN connect parameter** rather than `ALTER DATABASE`, and the pool closed at test end — then all three hazard classes evaporate: `SetMaxOpenConns` becomes test-local, session GUCs die with the pool, and the `ALTER DATABASE` sites can be deleted rather than accommodated.

This is the difference between the decisive lever converting ~130 files or ~110. It requires touching those 9 test files to drop their `ALTER DATABASE` line — **a scope question for the hub**, since the charter's hard rule ("a test that mutates schema or session/DB defaults must keep fresh-clone semantics") would otherwise pin them to clones on a technicality, when the correct fix is to stop the boilerplate mutation at the factory seam. Not absorbed unilaterally.

## 11. Lever 1 — reset primitive is DELETE, not TRUNCATE (charter prescribed TRUNCATE; measured wrong by ~20,000×)

The charter's lever 1 prescribes per-test `TRUNCATE ... RESTART IDENTITY CASCADE` as the reset. Implemented as written, it made the suite **dramatically slower**, not faster: `tests/integration/tenantdata` went 11.2s warm → 614.95s, with 2 of 4 tests failing on a 180s context deadline *inside the reset itself*. That is a ~55× regression on the package lever 1 exists to speed up.

Measured directly, same leased database (`metaldocs_test_lease_c76a97b14b`), same 59-table set, psql `\timing`, alternating so neither ordering nor cache can explain it:

| Reset primitive | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| `TRUNCATE <59> RESTART IDENTITY CASCADE` | **98,958 ms** | **168,632 ms** | — |
| `DELETE FROM <59>` (`session_replication_role = replica`) | **5.4 ms** | **1.6 ms** | **5.0 ms** |

**Mechanism.** `TRUNCATE` allocates a **new relfilenode per relation** and forces a synchronous `DataFileImmediateSync` fsync on each. A bare 8 KB `fsync()` on this host's Docker-Desktop/WSL2 volume costs **~0.9 s** (measured with `dd conv=fsync`), so the reset pays ~59 × ~1.7 s of fixed cost **regardless of how many rows exist**. `synchronous_commit=off` does not help: it governs WAL commit, not file-level durability under `fsync=on`. `DELETE` reuses the existing relfilenode, issues no per-relation fsync, and costs proportional to **rows** — and an integration test leaves a handful. The charter's instinct ("TRUNCATE is the fast bulk primitive") is true for large tables on real disks and exactly inverted here: cost is per-relation and fixed, and the table set is wide and nearly empty.

This is the same finding as §3 one layer down. §3 showed the enemy is not per-unit cost but **forced synchronous I/O under concurrency** (`DROP DATABASE` forcing a checkpoint). TRUNCATE is that same tax in a different costume. Lever 1's *structure* (leased DB, no per-test CREATE/DROP) survives intact; only its prescribed primitive changes.

`SET LOCAL session_replication_role = replica` suspends FK triggers for the reset tx, which buys back the ordering-freedom `CASCADE` was providing — so DELETE needs no topological sort. It also suspends the DB tripwire triggers, which is why it must be `SET LOCAL`, in a tx, on a dedicated admin connection that no test ever uses.

**Rejected:** disabling `fsync` on the shared dev postgres. It is a durability-affecting setting on a container other work depends on, outside this unit's boundary — and now moot.

### 11.1 The 6-table exclusion set was unsound — caught by this unit's own fail-loud assert

The exclusion set specified for the truncate list (§4) treated `metaldocs.tenants`, `public.templates_template`, and `public.templates_template_version` as static seed data. They are not: `testdb.NewTenant` (`factory.go`) inserts into `tenants`, and `testdb/fixtures.go` plus several tests insert into `templates_template`. Excluding them means test-created rows **survive every reset**, so a leased database drifts further from clone-equivalence the more it is reused — a silent isolation leak, i.e. precisely the false-green class the charter's HARD RULE exists to prevent.

It did not stay silent: the post-reset row-count invariant assert (specified as fail-loud per the no-fallback principle) caught it on the second test to reuse a lease — `metaldocs.tenants has 2 rows, want 1`. The guard built to prove the design was sound is what proved this part of it was not.

**Fix:** baseline-diff instead of exclusion. At lease-CREATE time — when the clone is by definition still identical to the template — snapshot those three tables' primary keys into schema `metaldocs_testkit`; reset then deletes only non-baseline rows. `metaldocs_testkit` is invisible to the reset scan because the scan restricts to `public` + `metaldocs`, which is load-bearing, not incidental. Only `role_capabilities`, `schema_migrations`, `river_migration` remain genuinely static exclusions. The invariant asserts stay exactly as they are.

### 11.3 Sequences — DELETE does not reset them; `ALTER SEQUENCE ... RESTART` does (hub Condition A)

`TRUNCATE ... RESTART IDENTITY` reset sequences; DELETE does not, so under lease reuse sequences advance monotonically and diverge from clone semantics. There are exactly **4** sequences in `public` + `metaldocs`, and in the template **all 4 have `last_value = NULL`** — never called. A clone therefore hands every test `nextval` = 1.

Two of the four carry user-visible semantics, so this is not hypothetical: `public.document_revisions_revision_num_seq` (revision numbering) and `metaldocs.audit_events_audit_sequence_seq` (the audit chain).

Chose hub's option (ii) over (i) deliberately: **restoring exact clone semantics is cheaper than the ledger sweep that would prove nobody currently depends on it** — and it is correct for tests that do not exist yet, whereas a proof about today's callers expires the moment someone writes an `assert revision_num = 1`. Sequence list derived at runtime from `pg_sequences` (same self-healing rationale as the table scan); `ALTER SEQUENCE ... RESTART` is catalog-only, no fsync. Verified: after RESTART, `last_value IS NULL` again — clone-equivalent.

### 11.4 Baseline-diff REPLACED by snapshot-and-restore (hub Condition B)

Hub's objection kills the PK-snapshot design from §11.1: PK-diff restores **presence, not content**. A test that UPDATEs the baseline tenant row leaves it mutated, and the row-count invariant passes because the count is unchanged — the same silent-leak class, one layer in.

**Why the fix is restore and not fail-loud:** under clone semantics a test updating the baseline tenant row is entirely **legal** — it is that test's private database. Failing loud would reject legal tests. The reset's job is to make the lease clone-equivalent again, so restoring is *completing the reset*, not substituting a value: the no-fallback principle is not in tension here.

Design (simpler than PK-diff, not more complex — no diff logic, no PK knowledge, no content hashing, no third class):
- At lease-CREATE time, while the clone is still identical to the template, snapshot full row content column-agnostically: `CREATE TABLE metaldocs_testkit.snap_<t> AS SELECT * FROM <t>` for the 3 test-written seeded tables.
- Reset treats those 3 exactly like the other 59 (unconditional `DELETE FROM`), then restores via `INSERT INTO <t> SELECT * FROM metaldocs_testkit.snap_<t>`.
- `role_capabilities`, `schema_migrations`, `river_migration` remain excluded — never written by tests.
- The reset scan's restriction to schemas `public` + `metaldocs` is what keeps `metaldocs_testkit` invisible to it. **Load-bearing, commented at the scan site** so nobody later widens the scan and silently deletes the snapshots.

### 11.6 `ALTER SEQUENCE ... RESTART` was MY error — `setval` is the primitive. Forced-sync I/O, third instance.

§11.3 instructed `ALTER SEQUENCE ... RESTART` and asserted it "catalog-only, no fsync". **False**, measured:

| Reset variant | COMMIT | tx total |
|---|---|---|
| `ALTER SEQUENCE ... RESTART` | 151–244 ms | 169–258 ms |
| no sequence step | 0.1 ms | 15 ms |
| **`setval(seq, start, false)`** | **0.08–0.33 ms** | **13–19 ms** |

`ALTER SEQUENCE ... RESTART` **rewrites the sequence relfilenode**, which forces a synchronous commit *even though this cluster runs `synchronous_commit=off`* — dragging one WAL fsync (150–660 ms) into every reset and 10×-ing the very reset it was added to. `setval` mutates the existing sequence page in place and pays nothing. `nextval` verified identical after both (= 1); only the cosmetic catalog `last_value` differs (1 vs NULL), which nothing reads.

**This is the unit's central finding landing a third time, and the third time it caught the author of the fix rather than the charter:**

| Instance | Primitive | Hidden cost |
|---|---|---|
| The outage (§3.3) | `DROP DATABASE` | forces a checkpoint |
| Lever-1 regression (§11) | `TRUNCATE` | 59 relfilenode swaps → 59 fsyncs |
| This (§11.6) | `ALTER SEQUENCE ... RESTART` | relfilenode rewrite → forced WAL fsync |

**Generalisable rule for the close-out:** on virtualized storage, prefer the primitive that **mutates in place** over the one that **replaces the file** — always, even when the file-replacing one is the "proper" DDL and reads as the cleaner intent. Every instinct that reaches for a clean primitive here reaches for a relfilenode swap. `DELETE` over `TRUNCATE`, `setval` over `ALTER SEQUENCE RESTART`, lease-reuse over `DROP`/`CREATE`.

Reset now **65–124 ms** end-to-end (bare tx 13–19 ms), inside the 80.2 ms of §11.5.

Lever 2 re-summons the exact forced-synchronous-I/O cost that lever 1 removed, and multiplies it by the parallelism factor.

**The charter's ranking is therefore wrong, and not by a little.** It reads "lever 2 strictly after lever 1", implying lever 1 *enables* lever 2. Measurement says lever 1 makes lever 2 **counterproductive**: lever 1's entire win is *not cloning per test*, and `t.Parallel` forces precisely that. Lever 2's real precondition is **lever 4** — only deterministic, adoptable slot leases make acquisition free enough for parallelism to pay. Correct order: **1 → 4 → 2**, with the pool cap as the parallelism budget.

Reverted (`git checkout HEAD -- tests/integration/approval/`, verified zero `t.Parallel` remain). The pilot cost ~4 minutes and killed a lever that would have shipped a slower, flakier suite. **Piloting one package before a ~100-site rollout is why this was caught and not shipped** — the same broad-mechanical-rollout shape that produced §11.12.

**Bonus corroboration for §12.8's refusal of the 7.4× headline.** The serial arm re-measured **46.5 s wall / 34.8 s package** here, against **31.1 s / 29.4 s** at the entry gate — *identical code*, ~1.5× apart, the only variable being accumulated cluster state (75 leases by now). Cluster load moves these numbers by ~1.5× on its own. Any before/after comparison whose arms sit in different cluster states is measuring the cluster, not the change.

### 11.16 Lever 4 HARDENED — adoption works, and it is NOT a speed lever

Implemented per the hub's ratified design: deterministic slot names `metaldocs_test_lease_<fp16>_<resetPolicyVersion>_<NN>` (NN = 00–15), per-slot `pg_try_advisory_lock` claim on a connection pinned for process lifetime, adopt-or-create, run-start = logical retirement only, physical DROP moved to an explicitly-invoked idle-only `GCRetiredDatabases`.

**The measurement (3 paired arms, same session, same host state, `-p=1 -parallel=1 -count=1`, all GREEN):**

| arm | wall | `lease_checkout` (52 tests) | `reset` | `ensure_template` |
|---|---|---|---|---|
| clone-run1 (creates slot) | 20.4 s | **0.95 s** | 3.82 s | 0.02 s |
| adopt-run2 | 23.0 s | **0.02 s** | 3.74 s | 0.02 s |
| adopt-run3 | 23.6 s | **0.03 s** | 4.36 s | 0.02 s |

**Adoption works exactly as designed: `lease_checkout` 0.95 s → 0.02 s (~47×).** Run 2 and run 3 paid no `CREATE DATABASE` at all — they adopted run 1's slot. That is the mechanism the hub ruled for, and it is confirmed.

**And it bought almost no wall time — say so plainly.** The adopt arms are *slower* than the clone arm (23.0/23.6 s vs 20.4 s). That gap is test-execution noise, not the factory: total factory cost is now ~4.2 s of a ~21 s run (reset ~73 ms/test, checkout ~0). Reading the wall column alone would support either "lever 4 is a 47× win" or "lever 4 is a 13% regression"; both are wrong, and only the phase trace distinguishes them. **This is the fifth time in this unit that the aggregate hid the mechanism.**

**Honest re-statement of what lever 4 is for.** Lever 1 already eliminated the per-*test* clone (52 clones → 1). Lever 4 eliminates the per-*process* clone — worth ~0.93 s per process, so ~30 s across a full suite of ~30 package processes. Modest. **Lever 4's real justification is correctness, not speed:**
1. **It removes the outage mechanism.** The old sweep executed `DROP DATABASE ... WITH (FORCE)` on the *same pinned connection holding the global template-build advisory lock* (`db.go:249` lock → `db.go:364` drop). A drop that wedged on `IPC:CheckpointStart` (measured >5 min, §11.10) blocked every other test process behind that lock. Retirement is now logical; nothing drops under that lock.
2. **It closes the §11.9 reclamation gap.** Random slot names died with the process that made them, so no future process could ever find them (75+ orphans, ~996 MB). Deterministic names are adoptable by construction.
3. **It is what unblocks lever 2** (see below).

**Deviations from the ratified design, surfaced not buried:**
- **`buildTemplate`'s drop stays under the global lock.** The ruling said "global lock released BEFORE any DROP". Taken literally that breaks `buildTemplate`, which must drop a partial/previous database *of its own exact name* before recreating it — serializing precisely that drop is why the lock exists. Read the ruling as targeting unbounded *foreign*-database drops under the global lock; that class is now gone. Flagged for hub.
- **One DROP added on the lease path**, in the incomplete-baseline rebuild (below). Bounded: needs a crash to reach, runs under the slot's exclusive claim, never under the global lock, serialized by `leaseCreateMu`.

**Three defects found reviewing the implementation — none surfaced by `go vet`, all found by reading:**

1. **`CREATE TABLE IF NOT EXISTS … AS SELECT` in the baseline heal path.** Postgres skips the `SELECT` entirely when the table exists — no error, no refresh. On an adopted slot the heal would then snapshot a **used, dirty** database as the "pristine" baseline that every future reset restores to: a permanent, silent false green, in the exact factory whose job is preventing them. Fixed: plain `CREATE TABLE` (fails loud with 42P07 if the pristine-state assumption is ever violated), a real completeness check (`leaseBaselineIsComplete` — every snapshot table, not just the schema, since a half-written baseline passes a schema-only check), and an incomplete baseline now **rebuilds the slot from template** rather than snapshotting it. Failing loud instead would be safe but would brick slot 00 for every future run until a human intervened.
2. **Retirement thrashed concurrent tracks.** `retireStaleTemplates` retired *every* non-current template unconditionally — including one a run on another branch is actively cloning from, clearing its ready marker and forcing it to rebuild mid-flight. Strictly better than the old code (which *dropped* it) but still the HARNESS §9.3a mutual-thrash. Fixed with a `NOT EXISTS (… pg_stat_activity …)` guard: only untouched templates retire, so concurrent tracks leave each other alone.
3. **A compat shim kept a lying test alive.** The implementation left `sweepStaleTemplates` delegating to `retireStaleTemplates` purely so `template_bounded_test.go` — which asserts the *old physical-drop* behaviour — would still compile. It would then fail at runtime, inviting the next reader to "fix" it by restoring the DROP that caused the outage. Shim deleted; test **re-homed, not relaxed** (see below). *(The subagent did the right thing here: it obeyed its edit boundary and reported the conflict rather than silently patching a file outside scope.)*

**`template_bounded_test.go` re-homed.** Its invariant splits in two under lever 4: *correctness* (a stale template can never be cloned from) is still automatic and is what the test now asserts — via the ready marker, with an explicit precondition check so the assertion cannot be vacuous. *Disk-space boundedness* is **no longer automatic**: it belongs to `GCRetiredDatabases`, which nothing calls. That is a real, deliberate trade — unbounded growth until a human runs GC, in exchange for never wedging the cluster from run-start bookkeeping — and the test says so instead of pretending otherwise. A test that proved boundedness would have to drop every retired database on the cluster, serialized, one forced checkpoint each: the exact stall this design exists to prevent.

**Why lever 2 was still blocked, and now is not.** `ensureLeaseSlotDatabase` ran with the pool mutex *unlocked*, so `-parallel=8` put 8 goroutines into 8 concurrent `CREATE DATABASE` — the precise 60.02 s timeout of §11.15. Adoption alone does not fix this: the *first* run must still create all 8. Added `leaseCreateMu`, serializing slot preparation. Cloning is I/O the host serializes anyway; doing it 8-wide converts a ~0.9 s operation into a timeout for all 8. First process now pays N clones back-to-back (~0.9 s each, once ever); every later process adopts at ~0.02 s.

**Lever 2 remains unproven, and any parallel arm measured today would prove nothing** — `t.Parallel` was reverted after the failed pilot (§11.15), so `-parallel=8` is currently *inert* on the approval package. Retry requires re-adding `t.Parallel` first (task #18).

**New finding (task #19): the existing ~996 MB is unreclaimable by design.** GC only touches databases whose COMMENT marker proves ownership. The ~75 orphan leases predate lever 4, carry no marker, and are therefore permanently invisible to GC. That is the "never drop a database you cannot prove you own" rule (HARNESS §9.3a) working as intended, not a bug — and it must **not** be weakened to sweep them. They need a deliberate one-time operator cleanup on an idle cluster.

### 11.17 Lever 2 retry — DEAD. Failed twice, two different mechanisms, same root cause

Hub ratified the re-sequence (1 → 4 → 2, charter correction #3) and imposed a guard: stagger or serialize slot construction so 8 concurrent CREATEs cannot recreate the §11.15 timeout. **Both halves of that guard were already in `8f6c30f7`** — `leaseCreateMu` serializes slot preparation, and growth is lazy (checkout claims a new slot only when the free list is empty *and* `held < cap`). So the retry ran with the guard in place.

`t.Parallel()` re-added to **52 of 53** tests (`t.Setenv`, shared-`*sql.DB`, and cluster-wide-assertion tests were excluded by criteria; the 53rd is a factory bypass — see below). Diff verified as exactly 52 `t.Parallel()` insertions, zero other changed lines. Paired arms, same session, `-p=1` in both so only *within-package* parallelism varies:

| arm | wall | package | Σ `lease_checkout` | Σ `reset` | result |
|---|---|---|---|---|---|
| `-parallel=1` | 22.6 s | **14.3 s** | 0.02 s | 3.29 s | 53 pass / 0 fail |
| `-parallel=8` run1 (cold slots) | 53.0 s | 44.9 s | 142.27 s | 32.95 s | 53 pass / 0 fail |
| `-parallel=8` run2 (warm slots) | 25.7 s | **17.9 s** | 3.98 s | **47.61 s** | 53 pass / 0 fail |

**The §11.15 failure is genuinely fixed: zero timeouts, zero failures, all arms green.** `leaseCreateMu` + adoption did what they were meant to do. Cold-slot run1 shows the cost honestly — Σ checkout 142.27 s while 7 slots are built one at a time, exactly the serialization the hub asked for, paid once ever.

**And lever 2 still loses.** Warm `-parallel=8` is **17.9 s vs 14.3 s serial — ~25% slower**, with no failure to blame this time.

**The mechanism is in the `reset` column, not the wall column.** Serial: 52 resets × ~73 ms = 3.29 s. Warm 8-way: 47.61 s → **~915 ms per reset, 12.5× slower each**. Eight-way overlap buys ~8×; each operation costs ~12.5× more; net loss. The resets are not competing for CPU — they are queuing at the same virtualized storage device. **This is the unit's thesis arriving from a third direction:** §11.15 said concurrency multiplies *clones*; this says concurrency multiplies *contention on every reset*. Removing the clone did not make the parallelism pay, because the clone was never what made it not pay.

**Lever 2 is closed, not deferred.** Charter had it as one of the two levers that *are* the unit. It is measured dead: twice, under two different mechanisms, after its stated precondition (lever 4) was satisfied exactly as ratified. The generalization matters more than the verdict — **the suite is I/O-bound, not CPU-bound.** `go test` already runs `-p=NumCPU` across packages, so cross-package concurrency saturates the device *before* within-package parallelism can contribute anything. There is no parallelism headroom left to buy on this host; the remaining wins are in *not doing I/O*, which is what levers 1 and 4 did.

**Confound stated, not hidden.** Arms ran par1 → par8-run1 → par8-run2, so par1 saw the cleanest cluster and some of its advantage is order (the §12.8 / §11.15 drift, ~1.5× on identical code). Order alone cannot explain a **12.5× per-reset latency blowup**, which is a mechanism signal, not a state signal — and the direction agrees with §11.15's independent measurement. Reverted (`git checkout HEAD -- tests/integration/approval/`, verified zero `t.Parallel` remain, tree clean).
