## Item 2 — M3 idempotency-key "drift" → NOT A DEFECT (finding + ESCALATION)

**ROADMAP premise:** `submit_service.go:81` raw-header passthrough; derivation
`ComputeIdempotencyKey` "lost in M3" — restore derivation or ratify.

**Finding (3 lines):**
1. `ComputeIdempotencyKey` was **deliberately deleted**, not lost — commit `fed69283`
   *"fix(documents): F-D4 require client idempotency key on submit, kill clock-derivation"*
   removed the server-clock-derived key (which let a retry seconds later mint a fresh key, bypass
   `UNIQUE(document_id, idempotency_key)`, and create a duplicate approval_instance).
2. The current code (`internal/modules/approval/application/submit_service.go:92-103`) threads the
   client `Idempotency-Key` header → `approval_instances.idempotency_key`, backed by the platform
   idempotency middleware (HTTP replay) + the DB UNIQUE constraint + a fail-closed service guard
   (`ErrIdempotencyKeyRequired`). This is the correct **global-maximum** end-state (F-D4 commit
   justified it under CLAUDE.md's Global-Maximum rule; two-stage review APPROVE; contract-first
   regen declaring `Idempotency-Key` required).
3. Restoring `ComputeIdempotencyKey` would **re-introduce the F-D4 duplicate-instance bug** — a
   regression. The `:81` line reference is stale (pre-3.1-kernel-extraction path/line).

**Disposition:** no code change. Emitted `ESCALATION` to hub recommending a lightweight ADR to
formally record the "client Idempotency-Key + DB UNIQUE + platform middleware" decision so future
roadmap passes do not re-flag it as drift. The decision is already ratified-by-commit-and-review;
the ADR only makes it discoverable.
